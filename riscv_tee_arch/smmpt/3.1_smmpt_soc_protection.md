# RISC-V SMMPT 架构深度教程

PART III · Chapter 13

# Debug、Trace、QoS 与 Confidential Computing

本章主题：为什么正确实现 SMMPT，仍然不足以保证一个 Supervisor Domain 的完整安全性？

在 Chapter 10–12 中，我们已经解决了三个核心问题：

- Memory Ownership： Linux 无法随意访问 OP-TEE 的私有物理内存。
- DMA Isolation： 不可信设备无法通过 DMA 绕过 Domain 的内存保护。
- Interrupt Isolation： 不同 Domain 的中断状态能够被隔离并正确投递。

现在假设这些机制全部工作正常，Linux 已经被攻击者完全控制，但 OP-TEE 运行在独立的 Supervisor Domain 中。

此时是否可以宣布整个 SoC 已经安全？

答案是：还不能。

因为攻击者虽然无法直接读取 OP-TEE 的私有内存，但仍可能通过以下途径破坏安全边界：

1. 利用 External Debug 读取 CPU 寄存器和安全内存。
2. 利用 Trace 捕获安全执行路径、地址或控制流。
3. 利用共享 Last-Level Cache、Memory Controller 等资源进行侧信道攻击或拒绝服务。
4. 对外部 DRAM 进行物理探测、篡改或重放。
5. 利用不完整的 Attestation，让远程用户信任实际上并不安全的平台。

本章的核心思想是：

SMMPT 是安全隔离架构的基础，但它既不是完整的 Confidential Computing 架构，也不是所有信息泄漏途径的统一解决方案。

我们将从实际工程问题推导出需要增加哪些安全机制，并进一步解释 RISC-V 为什么采用分层、可组合的设计。

# 13.2 为什么 Debug Interface 可能突破 SMMPT？

## 13.2.1 从一个实际攻击场景开始

假设我们有以下系统：

图中 Debug Access Path 是需要额外管理的安全入口，不能直接假定它受普通 S-mode 的 MPT 权限限制。

OP-TEE 正在执行 AES 或签名操作，密钥已经加载到 CPU 寄存器中。

假设攻击者拥有未经保护的 External Debug 权限。

他可能：

1. Halt 当前正在执行 OP-TEE 的 Hart。
2. 查看 PC、GPR 和调试可访问的 CPU 状态。
3. 通过 Debug Module 访问目标内存。
4. 修改指令或执行状态。
5. 继续运行系统，而不触发普通 Linux 访问 Secure Memory 的错误路径。

这样即使：

```
MPT_Linux[OPTEE_DDR] = No Access
```

仍然可能泄露安全数据。

为什么？

因为常规 RISC-V Debug Mode 具有非常高的权限，并不等价于普通 S-mode 程序发起的访问。

RISC-V Debug 规范中，Debug Mode 是特殊执行模式；未采用附加安全约束的调试实现可以获得接近或超过 M-mode 的访问能力。

于是得到第一条重要结论：

> 安全隔离的关键不只是阻止 Linux 访问 OP-TEE，还必须确保任何能够观察或修改 OP-TEE 状态的其他主体，都受到可信安全策略约束。

## 13.2.2 Debug Module 中存在不止一种访存路径

理解 Debug 安全，必须将几种路径分开。

```
External Debugger
       |
       v
Debug Module
       |
       +-- Abstract Command
       |
       +-- Program Buffer
       |
       +-- System Bus Access
```

### 路径 A：Abstract Command / Program Buffer

这类访问可能通过 Hart 内部执行或调试访问机制，读取寄存器、修改执行状态或执行指令。

关键在于：调试访问采用什么有效权限？对应的内存保护检查是否依然执行？

早期的 Debug 模型往往允许非常强的访问权限，因此普通 MPT 隔离未必成立。

### 路径 B：System Bus Access（SBA）

Debug Module 也可能直接成为 System Bus Master。

访问路径类似：

```
JTAG
  |
  v
Debug Module
  |
  | System Bus Access
  v
AXI / NoC
  |
  v
Secure DDR
```

注意，这里没有 Hart 执行普通 Load/Store。

因此不能认为 Hart 上的 `mmpt` 会自然保护这条访问。

必须在 Debug Module、系统互连或独立的物理访问控制器中建立对应的硬件限制。

这与 Chapter 11 的 DMA 隔离有很强的相似性：所有能够发起物理内存访问的 Master，都必须有可靠的安全归属与检查路径。

## 13.2.3 External Debug Security 试图如何解决这个问题？

RISC-V 独立的 External Debug Security 规范正在解决传统 Debug 模型中的权限问题。

它提出的机制包括：

- 按权限等级分别控制 External Debug/Trace。
- 对 Debug Module 的系统总线访问施加安全保护。
- 限制 Program Buffer 和 Abstract Command 的访问权限。
- 引入平台可信控制以及调试授权状态。
- 让较低权限软件的调试，不必自动意味着能够调试 M-mode。

这些功能属于独立的 Debug Security 规范体系，而不应再作为当前 SMMPT 扩展的直接组成部分。

### 面向 SoC 设计的三个 Debug 安全等级

| 等级                | Debug 权限                  | 适用场景            |
| ----------------- | ------------------------- | --------------- |
| Root Debug        | 可能观察 M-mode/RDSM 与全部受控安全域 | 芯片厂商受控 bring-up |
| Non-root Debug    | 仅观察被授权的软件范围               | Linux、驱动调试      |
| Production Locked | 不允许未经授权的外部调试              | 量产安全部署          |

这是安全策略分类，不是规范定义的三个固定硬件模式。

最重要的是：

Linux 的调试权限不能自动提升成 OP-TEE 的调试权限，OP-TEE 的调试权限也不能自动提升成 RDSM 的调试权限。

# 13.3 如何设计真正安全的 Debug Authorization？

前面只解释了为什么危险，现在开始分析实际工程方案。

假设 SoC 同时面向研发和量产两个阶段。

研发阶段希望使用 TRACE32 或 GDB 调试：

```
Linux / OpenSBI / OP-TEE
```

量产阶段则要求保护：

```
Root Key
Device Identity
Secure Boot State
OP-TEE TA Private Key
Confidential VM Memory
```

显然不能使用一套永远开放的 Debug 策略。

## 13.3.1 Debug Authorization 应当由 Root of Trust 控制

推荐采用以下架构：

```
External Debugger
       |
       | Authentication / Authorization
       v
Hardware Root of Trust
       |
       | Approved Security Policy
       v
Debug Security Controller
       |
       +-- M-mode Debug Policy
       |
       +-- Non-M-mode Debug Policy
       |
       +-- Trace Policy
       |
       +-- Debug Module SBA Policy
```

例如，一个生产环境的请求：

```
Request:
  Debug Linux Domain only

Allowed:
  Linux Registers
  Linux Memory
  Linux Execution

Denied:
  OP-TEE Private Registers
  OP-TEE Memory
  RDSM Internal State
  Secure Key Storage
```

真实系统能否做到这样精细的隔离，取决于 Hart Debug Security 能力、Debug Module 访问控制和 SoC 系统安全设计。

不能只是 Firmware 软件宣称禁止读取，而硬件依然允许 Debug Module 越权访问。

## 13.3.2 调试授权不仅需要身份认证

假设一个厂商工程师通过数字证书获得了 Debug 权限。

是否意味着可以永久访问全部安全状态？

当然不是。

调试授权至少应明确：

| 参数                 | 含义                                       |
| ------------------ | ---------------------------------------- |
| Identity           | 谁获得调试权限                                  |
| Target             | 哪个设备、Hart 或 Domain                       |
| Scope              | 允许读取什么、修改什么                              |
| Lifecycle          | Development / Manufacturing / Production |
| Validity           | 授权有效期及重新验证策略                             |
| Revocation         | 如何撤销权限                                   |
| Attestation Impact | 调试状态是否影响平台可信声明                           |

例如：

```
Debug Authorization:
  Device       = Device-A
  Domain       = Linux
  M-mode       = Denied
  OP-TEE       = Denied
  Trace        = Denied
  Production   = Restricted
```

即便通过身份认证，也只能获得这一有限范围。

## 13.3.3 为什么 Debug Policy 应该进入 Attestation？

这是本章中第一个非常值得从架构角度思考的问题。

假设服务器向远程客户声明：

```
Your workload runs inside
a Confidential VM.
```

客户完成了 Attestation，确认 VM 软件镜像正确。

但服务器管理员随后打开 External Debug，可以读取 Confidential VM 的内存。

那么，之前的可信声明就不完整，甚至已经失效。

因此 Attestation 不仅需要证明：

```
Software Image = Expected Image
```

还需要证明与安全承诺相关的配置，例如：

```
Debug Enabled?
Trace Enabled?
Firmware Version?
Domain Isolation Enabled?
Trusted Device Configuration?
```

对于会破坏机密性的 Debug 开启流程，一个常见的安全设计是要求重启受影响组件、使原来的证明状态失效或重新测量，并阻止以前的 Attestation Evidence 被继续用于建立信任。

RISC-V Security Model 对受控 External Debug 和测量状态之间的关系也提出了相应安全要求。

## 13.3.4 Self-hosted Debug 与 External Debug 的区别

这一点在实际 OS 开发中很容易忽略。

Linux 上的：

```
gdb ./application
```

通过 `ptrace` 等接口调试用户态程序，属于 Self-hosted Debug 的典型场景。

它与：

```
JTAG -> Debug Module -> Halt Hart
```

不是同一条路径。

Self-hosted Debug 通常由 OS 内部的软件权限模型控制：

```
Linux Kernel
    |
    v
ptrace
    |
    v
Linux User Process
```

只要 Linux 本身不能跨越 SMMPT Domain 边界，Linux 内部的 Self-hosted Debug 并不天然意味着可以读取 OP-TEE。

但这里必须审查硬件 Trigger、Performance Counter、Indirect CSR 等共享资源，防止调试状态跨域遗留。

此外，也不能把 Linux `ptrace` 访问控制误当成 External Debug 安全授权。

本节总结：Debug 的根本问题，是谁拥有观察和修改系统内部执行状态的权力。它属于安全架构的一部分，而不是单纯的开发工具配置。

# 13.4 Trace：不读取内存，也可能泄露机密

## 13.4.1 Trace 与 Debug 的差别

Debug 通常可以停止目标执行，并主动检查或修改系统状态。

Trace 则侧重于记录执行过程。

例如：

```
OP-TEE Trusted Application
       |
       | Execute instructions
       v
CPU Trace Encoder
       |
       | Execution / Control-flow Trace
       v
Trace Buffer / Trace Sink
       |
       v
External Trace Tool
```

Trace 不一定记录完整指令或所有数据值，但根据实现，它可能暴露：

- 执行过的代码地址或分支信息。
- 函数调用路径。
- 异常和中断发生时机。
- 任务和上下文切换行为。
- 访存地址或其他微架构事件。
- 高精度时间信息。

为什么这些信息可能敏感？

假设一个 TA 根据密钥进行条件分支：

```
if (key_byte & 1)
    process_path_a();
else
    process_path_b();
```

攻击者即使无法读取 `key_byte`，也可能通过 Branch Trace 推断出条件分支的结果。

这是一个故意构造的、存在秘密相关分支的例子；正规的常数时间密码实现应避免这种实现方式。

现在假设外部 Trace Encoder 能同时捕获 Linux 和 OP-TEE。

即使 MPT 已经完全阻止 Linux 对安全内存的直接读取，Trace 仍可能使 OP-TEE 的信息暴露给未授权观察者。

因此：

\\[ \text{Memory Isolation} \not\Rightarrow \text{Execution Trace Isolation} \\]

## 13.4.2 Trace 数据流中的三个信任边界

要建立完整 Trace 安全模型，我建议把 Trace 拆成三个阶段。

| 阶段                  | 关键问题                     |
| ------------------- | ------------------------ |
| Trace Configuration | 谁能开启、关闭、修改过滤条件？          |
| Trace Generation    | 哪些 Domain 的执行信息会被捕获？     |
| Trace Transport     | 谁能访问 Trace Buffer 和输出接口？ |

例如：

```
Hart Execution
     |
     v
Trace Encoder
     |
     v
Trace Transport
     |
     +-- On-chip Trace SRAM
     |
     +-- Trace DMA
     |
     +-- External Trace Port
```

即使 Trace Encoder 对 Domain 的过滤完全正确，如果 Trace Buffer 可以被 Linux 读取，仍然可能泄漏之前留下的 OP-TEE Trace Data。

同样，如果 Trace DMA 是一个不受 I/O 保护的 Bus Master，也可能破坏系统的隔离边界。

所以，Trace 安全并不是给 CSR 增加一个 Enable Bit 就结束了。

必须同时保护控制面、数据面，以及从旧 Domain 切换到新 Domain 时的残留状态。

## 13.4.3 Domain Switching 中如何处理 Trace State？

假设 Hart 0：

```
T0: Running Linux
T1: Enter RDSM
T2: Running OP-TEE
T3: Return to Linux
```

一个参考设计是：

```
Linux -> RDSM
    |
    +-- Block unauthorized trace collection
    +-- Stop or drain relevant trace pipeline
    +-- Save Linux-authorized trace context
    +-- Select OP-TEE trace policy
    +-- Clear or segregate stale trace state
    |
    v
OP-TEE Execution
    |
    +-- Trace disabled unless explicitly allowed
    |
    v
RDSM -> Linux
    |
    +-- Stop/drain protected-domain trace path
    +-- Restore Linux trace context
    +-- Resume authorized tracing
```

这里的核心安全不变量是：

\\[ TraceOutput(D_A) \cap ObservableBy(D_B) = \varnothing \\]

其中 \\(D_A\\) 和 \\(D_B\\) 是彼此不信任的 Domain。

这个表达式描述的是设计目标，而不是仅依靠关闭 Trace Enable 就能自动证明的性质。

规范边界提醒： 早期 SDAP 文档将 `Smsdedbga`、`Smsdetrca` 及 `msdcfg.SEDA/SETA` 用于每个 Domain 的 Debug/Trace Allow 控制，但这些章节已从当前主规范构建中排除。当前实现应参考独立的 RISC-V External Debug Security / Secure Trace 方案及 SoC 安全控制器，而不应默认芯片已经实现那些旧位域。

## 13.4.4 OP-TEE 实际工程中如何处理 Trace？

假设当前需要使用 TRACE32 定位 OP-TEE 中的一个异常。

我会把可用的调试方式划分为：

| 调试手段                       | 典型安全影响          |
| -------------------------- | --------------- |
| OP-TEE 内部安全日志              | 需要审查日志内容与输出路径   |
| Secure Panic Dump          | 可能包含敏感上下文       |
| Linux `dmesg`              | 只能观察被允许公开的信息    |
| External Instruction Trace | 可能泄露安全执行路径      |
| Halt + Register Dump       | 可能直接暴露密钥和上下文    |
| System Bus Memory Dump     | 可能绕过普通 CPU 访存保护 |

因此，对于研发环境可以采用 Debug-enabled Firmware、独立的测试密钥和受控调试策略。

对于量产环境，则应该将安全调试授权、日志脱敏、Trace Buffer 访问限制以及 Attestation 状态作为完整方案设计。

不要简单地依靠：

```
#define CFG_TEE_CORE_LOG_LEVEL 0
```

就认为已经完成了安全调试控制。

这个宏只能影响 OP-TEE 的一部分软件日志行为，不能控制芯片级 External Debug 和 Trace。

# 13.5 QoS、Shared Cache 与性能侧信道隔离

这是 Chapter 13 中最值得深入的硬件架构专题之一。

## 13.5.1 为什么 QoS 会成为 Security Architecture 的一部分？

先看普通多核 SoC 的资源结构。

即使 Linux 与 OP-TEE 使用不同的物理内存页面，它们仍可能共享：

- Last-Level Cache（LLC）
- Cache Replacement Policy
- Memory Controller
- DRAM Channel
- Interconnect
- Prefetcher
- 某些共享性能计数器

假设 Linux 不断执行大量缓存访问：

```
for (;;) {
    touch_large_buffer();
}
```

这可能大量占用 LLC 和 DRAM Bandwidth。

与此同时 OP-TEE 正在执行：

```
Secure Operation
    |
    +-- Access Secure Memory
    +-- Cryptographic Computation
    +-- Return Result
```

Linux 可能对 OP-TEE 产生两类影响。

第一类：Availability / Performance Interference

Linux 通过持续争用 Cache 和 Memory Bandwidth，使 OP-TEE 响应时间增加。

第二类：Information Leakage

Linux 根据资源竞争、执行延迟或被授权观察的资源统计，推测 OP-TEE 的执行行为。

二者是不同的安全问题：

- DoS 主要破坏 Availability。
- Side Channel 可能破坏 Confidentiality。

QoS Resource Allocation 主要有助于限制资源争用，并可配合监控隔离减少特定泄漏面，但并不天然消除所有缓存侧信道。

## 13.5.2 从 Prime+Probe 理解共享 Cache 的问题

我们考虑一个简化的 Cache Side-channel 场景。

假设攻击者控制 Linux，安全计算运行于 OP-TEE。

攻击者无法读取 OP-TEE 的物理地址。

但攻击者可以访问自己的 Buffer，并测量 Cache 访问延迟。

一个抽象攻击过程是：

```
Step 1:
  Linux fills selected cache sets

Step 2:
  OP-TEE runs secret-dependent workload

Step 3:
  OP-TEE activity may evict Linux cache lines

Step 4:
  Linux probes its own cache lines

Step 5:
  Linux observes timing differences
```

整个过程没有 Linux 对 Secure DDR 的直接访问。

因此，SMMPT 可能完全没有产生 Access Fault。

这说明：

MPT 保护的是内存访问权限，不是共享微架构资源上的全部信息流。

如果安全要求包括防范特定 Cache Side Channel，除了 MPT，还必须考虑 Cache Partition、Time Partition、Speculation Control、Constant-time Implementation 等机制。

## 13.5.3 RISC-V 如何通过 QoS 标识管理资源？

先介绍三个重要标识。

| 标识   | 全称                        | 职责               |
| ---- | ------------------------- | ---------------- |
| RCID | Resource Control ID       | 标识资源分配策略         |
| MCID | Monitoring Counter ID     | 标识资源使用统计         |
| QRID | QoS Register Interface ID | 标识 QoS 配置与监控命名空间 |

可以这样理解：

```
RCID:
  How much resource may I use?

MCID:
  Which monitor accounts for my usage?

QRID:
  Which QoS configuration namespace applies?
```

在支持这些机制的 SoC 中，请求进入 LLC/Memory Controller 时，会携带相应的 QoS 属性。

于是资源控制器可以执行不同的容量及带宽策略。

例如：

```
Linux:
  QRID = 0
  RCID = 5
  MCID = 5

OP-TEE:
  QRID = 1
  RCID = 2
  MCID = 2
```

同一个 RCID 数值也可以在不同 QRID 中指代不同的资源配置。

这依赖于硬件支持的 QRI 命名空间。

## 13.5.4 `Smqosid`、`Ssqosid` 和 `Smsdqosid` 的区别

这里非常容易混淆，因为扩展名称相似，但职责不同。

| 扩展          | 关键寄存器              | 核心用途                            |
| ----------- | ------------------ | ------------------------------- |
| `Ssqosid`   | `srmcfg`           | S/HS-mode 设置 RCID、MCID          |
| `Smqosid`   | `mrmcfg`           | M-mode 请求的 QoS 标识               |
| `Smsdqosid` | `mnrmcfg`、`msdcfg` | RDSM 限制与映射各 Domain 的 QoS 标识     |
| CBQRI       | Memory-mapped QRI  | Cache/Memory Controller 资源分配及监控 |

其中：

```
mrmcfg CSR = 0x381
mnrmcfg CSR = 0x781
srmcfg CSR = 0x181 (RV64)
msdcfg CSR = 0x74E
```

在 RV64 平台上，`Ssqosid` 的 `srmcfg` 可以帮助 OS 管理它自己拥有的 Workload QoS。

但如果 Linux 与 OP-TEE 是不同的 Supervisor Domain，就不能让 Linux 随意选择 OP-TEE 的 RCID 和 MCID。

这正是 `Smsdqosid` 需要解决的问题。

当前 SDAP 规范定义了 `mnrmcfg` 与 `msdcfg` 的相关字段，以及通过它们生成有效 RCID/MCID 的规则。

## 13.5.5 结合实际位域理解 `Smsdqosid`

我们来做一个真实的计算案例。

假设资源控制器支持：

```
RCIDLEN = 5
Total RCIDs = 32
```

RDSM 希望分配：

```
Linux:
  Effective RCID = 0–23

OP-TEE:
  Effective RCID = 24–31
```

注意，Linux 和 OP-TEE 可以使用同一个 QRI，但必须保证能够选择的有效 RCID 范围互不重叠。

### 为 OP-TEE 设置低位可写的 RCID

假设配置：

```
mnrmcfg.RCID = 24
msdcfg.SRL   = 3
msdcfg.SSRM  = 0
```

这里 `SRL = 3` 表示 S-mode 软件可以选择三个低位。

规范定义：

\\[ MASK = 2^{SRL}-1 \\]

有效 RCID 为：

\\[ RCID\_{effective} = (mnrmcfg.RCID \mathbin{\&} \sim MASK) \\;|\\; (srmcfg.RCID \mathbin{\&} MASK) \\]

带入：

```
MASK = 0b00111

mnrmcfg.RCID = 24
             = 0b11000

srmcfg.RCID = 0b00101
            = 5
```

计算：

```
0b11000 & ~0b00111 = 0b11000

0b00101 &  0b00111 = 0b00101

Effective RCID = 0b11101 = 29
```

因此，OP-TEE 可以动态选择：

```
srmcfg.RCID = 0..7
```

但是最终送到共享资源控制器的 RCID 被硬件限制在：

```
24..31
```

这就建立了两个层级的控制：

- RDSM 决定 Domain 可以使用的 RCID 范围。
- OP-TEE 可以在该范围内自行管理自己的 Workload。

这种“Root Policy + Domain-local Flexibility”的设计非常值得学习。

它避免了每次 Workload QoS 调整都必须陷入 M-mode，同时又不允许 Domain 超越 RDSM 分配的资源命名空间。

### 为 Linux 分配 RCID 0–23

规范也提供 `SSRM = 1` 的映射方式。

例如：

```
RCIDLEN = 5
SRL     = 3
SSRM    = 1
```

此时 Linux 可在 `srmcfg.RCID` 选择的合法范围为：

\\[ 0 \ldots (2^5 - 2^3 - 1) \\]

也就是：

```
0..23
```

这样就可以与 OP-TEE 的 24–31 范围形成分离。

MCID 可采用相应的 `SML`、`SSMM` 和 `mnrmcfg.MCID` 机制。

注意，这里隔离的是 Resource ID 的分配范围，还需要资源控制器本身正确配置 QoS 策略，才能形成期望的容量及监控隔离。

## 13.5.6 CBQRI：如何真正管理 LLC 和 DRAM Bandwidth？

前面我们只建立了标识。

现在必须让资源控制器理解这些标识。

CBQRI 提供 Capacity Controller 和 Bandwidth Controller 的配置机制。

例如：

```
LLC Capacity Controller
       |
       +-- QRID 0: Linux
       |
       +-- QRID 1: OP-TEE
```

假设一个 LLC 支持八个 Capacity Blocks。

RDSM 希望：

```
Linux:
  Blocks 0–5

OP-TEE:
  Blocks 6–7
```

这可以通过 Machine QoS Register Interface（MQRI）提供的资源限制配置实现，前提是硬件支持相应的 QRI 资源预留能力。

当前规范定义了 `CONFIG_QRI_LIMIT` 操作，用于由 M-mode 对不同 QRI 的资源配额实施限制。

### 为什么还需要保护 Monitoring Counter？

假设 OP-TEE 有专用的 MCID。

如果 Linux 可以随意读取 OP-TEE 的资源使用计数器，那么 Linux 就可能看到：

```

```

攻击者可能依据统计变化推断 OP-TEE 的 Workload 阶段。

因此，不仅资源配额需要保护，资源监控状态也需要隔离。

当前规范明确提出，某个 Domain 或 RDSM 的资源使用信息不应暴露给其 TCB 之外的实体，相关分配策略也不能由其他实体随意修改。

## 13.5.7 如果硬件只有一个 QRI，该怎么办？

这是一个非常实际的问题。

假设 SoC 只有：

```
QRID = 0
```

但存在 Linux 和 OP-TEE 两个 Domain。

如果把整个 QoS MMIO 区域直接映射给 Linux，它可能：

- 修改 OP-TEE 的 Cache Quota。
- 读取 OP-TEE 的 Monitoring Counter。
- 将自己的 RCID 配置成不属于自己的值。
- 修改共享 Memory Controller 的带宽配置。

因此 RDSM 应当控制这个 QRI。

Domain 通过受控的软件接口请求配置：

```
Linux / OP-TEE
      |
      | QoS Configuration Request
      v
RDSM
      |
      | Validate RCID/MCID and ownership
      v
CBQRI MMIO
```

规范允许 RDSM 通过 SBI 接口或虚拟 QoS Register Interface 模拟来中介访问。

例如可设计一个参考 API：

```
int rdsm_qos_configure(
    uint32_t caller_domain,
    uint32_t local_rcid,
    uint32_t allocation,
    uint32_t monitoring_id);
```

这不是一个已经标准化的 SBI 函数。

RDSM 必须验证调用者，不能仅信任调用参数中的 `caller_domain`。

另外，Domain 在切换时需要处理 `mnrmcfg`、`msdcfg` 相关配置；如果共享资源分配策略具有残留状态，还需要保证新 Domain 不会继承旧 Domain 的未授权 QoS 配置。

## 13.5.8 从源码与汇编理解 QoS Context

对于需要研究汇编级机制的工程师，下面这段 RV64 代码值得关注：

```
# Conceptual RV64 M-mode code
# a0: validated mnrmcfg value
# a1: validated msdcfg value

csrw  0x781, a0       # mnrmcfg
csrw  0x74e, a1       # msdcfg
```

它演示两个 M-mode CSR 的写入方式，并不构成完整、安全的 Domain Switch。

在真实切换中，需要保证：

1. 新配置来自 RDSM 可信上下文。
2. 所有保留位与 WARL 字段按硬件规则处理。
3. MPT、Interrupt Domain、QoS 和 CPU Context 一致。
4. 旧资源统计及权限不会暴露给目标 Domain。
5. 符合架构规定的同步与程序顺序要求。

下面的指令则通常由有权管理自己 QoS 状态的 S-mode 软件使用：

```
csrw  0x181, a0       # srmcfg (RV64)
```

它修改的是 S/HS-mode 使用的 QoS 标识，而不是修改 RDSM 已经建立的跨域资源授权边界。

这一点和 `satp` 与 MPT 的分工非常相似：

```
Domain:
  Manages its own workloads

RDSM:
  Limits what the domain may control
```

## 13.5.9 QoS 能否真正消除 Cache Side-channel？

不能作这样的保证。

即使两个 Domain 已分配不同的 LLC Capacity Blocks，仍然可能存在：

- 共享 Memory Controller 的延迟差异。
- Cache Bank 或内部端口争用。
- Prefetcher 和其他微架构资源影响。
- Speculative Execution 相关泄漏。
- 内存访问时序上的信息泄漏。

Cache Partition 可以显著缩小一些共享资源攻击面，但其实际安全属性取决于分区粒度、Cache 设计及威胁模型。

尤其要区分：

QoS Isolation 通常是资源容量和带宽管理机制，而严格的 Side-channel Non-interference 是更强的安全目标。

如果要证明某类秘密相关微架构侧信道已经受到有效缓解，需要额外的安全分析、代码约束及测量验证。

# 13.6 Memory Encryption：MPT 为什么不能替代内存加密？

## 13.6.1 从一个物理攻击场景开始

假设 OP-TEE Private Memory 位于：

```
PA: 0x9000_0000
Size: 128 MB
```

系统已经配置：

```
Linux MPT:
  No Access

OP-TEE MPT:
  RW
```

这能够阻止 Linux 通过普通 CPU 访问该区域。

但是假设攻击者拥有针对外部 DRAM 的物理攻击能力，例如能够观察某些内存总线信号或窃取特定条件下的 DRAM 数据。

MPT 是否能够保护这些数据？

不能。

因为 MPT 检查发生在 SoC 内部的内存访问控制路径上，而 DRAM 中的数据是否经过加密，是另一项安全机制负责的。

因此需要明确两种保护目标：

| 机制                | 主要安全目标                |
| ----------------- | --------------------- |
| SMMPT             | 阻止未授权 Domain 发起物理内存访问 |
| Memory Encryption | 防止特定物理攻击者直接获取明文       |
| Memory Integrity  | 检测不被允许的内存数据篡改         |
| Replay Protection | 防止攻击者重放旧的有效数据         |
| Attestation       | 证明系统的身份、软件与安全配置满足策略   |

这些能力既可能相互依赖，也可能由不同的硬件模块提供。

当前 Supervisor Domains 规范将内存加密视为独立、与用途及平台有关的机制，而非 SMMPT 必然提供的功能。

## 13.6.2 Memory Encryption Engine 的工作位置

在一种典型的 SoC 设计中：

```
RISC-V Hart
     |
     | VA -> PA
     v
MMU / MPT
     |
     | Authorized Physical Request
     v
Cache Hierarchy
     |
     v
Memory Encryption Engine
     |
     | Ciphertext
     v
External DRAM
```

这里的模块顺序仅用于理解逻辑。实际加密引擎可能集成在 Memory Controller 或其他存储路径位置，并且 Cache、DMA 和 Encryption Engine 的交互方式取决于芯片设计。

假设：

```
OP-TEE plaintext:

0x90000000:
  11 22 33 44 55 66 77 88
```

在外部 DRAM 中，可能存储的是：

```
Ciphertext:

0x90000000:
  A7 8C 19 2D ...
```

外部攻击者即使直接读取 DRAM，也不能仅凭该密文得到 OP-TEE 的明文。

但这里存在一个更深入的问题。

如果不同 Domain 使用不同的 Memory Encryption Key，硬件应该如何知道当前访问属于哪个加密上下文？

这就引出了下一节。

## 13.6.3 为什么不同 Domain 需要不同的加密上下文？

考虑一种平台特定的 Memory Encryption 方案。

```
Linux:
  Encryption Key = K_linux

OP-TEE:
  Encryption Key = K_tee
```

假设物理地址：

```
PA = 0x9000_0000
```

原本属于 Linux，随后按照 Chapter 10 的协议转移给 OP-TEE。

这里存在两个独立的变化：

```
Access Permission:
  Linux -> OP-TEE

Encryption Context:
  K_linux -> K_tee
```

改变 MPT 权限，不等于自动完成内存数据的加密上下文切换。

如果硬件直接使用 `K_tee` 解密原本由 `K_linux` 加密的 DRAM 数据，得到的通常不是有效的原始明文，而且在提供完整性保护的系统中还可能触发认证或完整性错误。

因此，Memory Ownership Transfer 可能需要同时完成：

1. 撤销旧 Domain 的 CPU/DMA 权限。
2. 等待旧的访存事务和缓存状态完成同步。
3. 清除或转换旧数据。
4. 重新建立目标加密上下文的内存状态。
5. 初始化与该上下文关联的完整性或 Replay Metadata。
6. 授予新 Domain 访问权限。

如果只是简单执行：

```
MPT_Linux[P] = Deny
MPT_OPTEE[P] = RW
```

那么在包含不同加密上下文的系统中，这个协议仍然是不完整的。

## 13.6.4 Confidentiality、Integrity、Replay Protection 为什么不能混为一谈？

设想攻击者可以控制外部 DRAM 数据。

### 攻击 A：读取 DRAM

攻击者看到密文：

```
Ciphertext = Encrypt(K, Plaintext)
```

如果加密方案正确、密钥未泄漏，攻击者不能由此直接得到明文。

这主要是 Confidentiality。

### 攻击 B：篡改 DRAM

攻击者修改密文的某些 Bit。

单纯的内存加密不一定能够检测这种行为。

如果缺少完整性验证，可能产生错误明文或其他不可接受的行为。

因此需要 Memory Integrity 机制。

### 攻击 C：重放 DRAM

假设某个安全计数器原本经历：

```
Counter = 100
Counter = 101
Counter = 102
```

攻击者保存了 Counter=100 时的有效密文，随后把旧密文写回。

即使该数据曾经具有有效的完整性标签，也不能说明它是当前最新的数据。

因此需要额外的 Replay Protection，例如与受保护状态关联的版本、计数器或认证树机制。

这一点与 Chapter 10 的 Generation 和 Ownership 转移有相似的设计思想：不仅要验证“数据属于谁”，还要验证“数据属于哪个生命周期”。

但它们处于不同的保护层次，不能直接互相替代。

# 13.7 Physical Address Metadata Selection：如何选择正确的安全上下文？

这一节属于前沿架构设计内容，需要特别强调：`Svpams` 曾出现在规范仓库，但当前不属于构建中的主规范内容。以下重点解释其设计动机，而不是将它作为已经定稿的 ISA 功能。

## 13.7.1 单纯使用 SDID 选择加密密钥，会遇到什么问题？

假设：

```
Linux Domain:
  SDID = 1
  Key = K1

OP-TEE Domain:
  SDID = 2
  Key = K2
```

系统设计如下：

```
Memory Request
      |
      v
Current Domain
      |
      v
Encryption Context = Key(SDID)
```

对 Private Memory 来说，这种思想容易理解。

例如：

```
OP-TEE -> OP-TEE Private DDR
              |
              v
            Use K2
```

但如果 OP-TEE 需要读取 Linux 和 OP-TEE 都能访问的 Shared Memory，该怎么办？

```
Linux writes Shared Page with K1
       |
       v
Shared DRAM
       |
       v
OP-TEE reads Shared Page with K2
```

如果二者使用不同密钥解释同一个密文，当然无法正常共享明文。

一种方案是为共享页面分配独立的加密上下文：

```
Private Linux:
  K1

Private OP-TEE:
  K2

Shared Linux/OP-TEE:
  K_shared
```

于是 Memory Encryption Context 不能仅由 SDID 唯一决定。

它还取决于：

- 访问的是 Private 还是 Shared Memory。
- Shared Memory 的参与者集合。
- VMID/ASID 等可能参与策略的上下文。
- 物理页面当前的加密状态。
- 其他平台定义的安全属性。

这正是 Physical Address Metadata Selection 的设计动机。

## 13.7.2 `Svpams` 的概念性设计

早期 `Svpams` 设计中，Page Table Entry 可以携带一个 4-bit PAMS 字段，用于选择至多 16 个元数据限定符。

这些限定符可能进一步由平台解释为 Memory Encryption Context 或其他地址相关属性。

该草案讨论过：

```
PTE.PAMS
    |
    v
Metadata Qualifier
    |
    v
Platform-specific Metadata
    |
    v
Memory Security Engine
```

例如：

| PAMS | 参考含义                 |
| ---- | -------------------- |
| 0    | 默认域私有加密上下文           |
| 1    | 全局共享上下文              |
| 2    | Linux ↔ OP-TEE 共享上下文 |
| 3    | 特定 VM 私有上下文          |

这些 PAMS 值的语义是教学示例，不是当前规范指定的标准编码。

草案也讨论过通过 `menvcfg`、`henvcfg` 控制元数据机制，以及将元数据与地址转换缓存结合的方式。

## 13.7.3 Metadata 与 MPT 的关系

最重要的是把两个问题分开：

```
MPT:
  Is this access permitted?

Metadata Selection:
  What security context applies
  to this authorized access?
```

例如：

```
Hart executing OP-TEE
       |
       | Load VA
       v
Page Table Translation
       |
       +-- Physical Address
       +-- PAMS (conceptual)
       |
       v
MPT Check
       |
       | Allowed?
       v
Memory Security Engine
       |
       | Select validated cryptographic context
       v
Physical Memory
```

其中的“PAMS 到加密上下文”映射必须受到可信策略约束。

否则不可信软件可以故意选择其他 Domain 的加密上下文。

所以不能简单地认为只要把 Key ID 放进页表，系统就安全了。

必须解决以下问题：

1. 谁可以选择某个加密上下文？
2. Key ID 是否必须与当前 Domain 绑定？
3. 共享上下文如何授权？
4. TLB 中缓存的 Metadata 如何失效？
5. DMA 设备如何获得相同的上下文信息？
6. 页面回收之后，旧上下文能否被重新使用？
7. 加密状态如何与 MPT Memory Ownership 保持一致？

## 13.7.4 物理地址 Metadata 为什么不是普通 PTE Permission？

传统的页表权限通常包括：

```
R / W / X
```

它们回答是否允许访问。

Metadata 则可能影响访问语义，例如：

```
Memory Encryption Context
Data Integrity Domain
Confidentiality Attribute
Platform-specific Memory Tag
```

这里甚至可能产生不同硬件状态之间的耦合。

比如，页表已经更新了 Metadata，但 TLB 仍缓存旧值；MPT 权限已经更新，但 Memory Controller 仍使用旧的加密上下文。

因此一个完整的安全内存转移机制，可能不仅需要：

```
MFENCE.PA
```

还需要地址转换、元数据缓存和内存安全引擎对应的同步机制。

具体指令及同步顺序取决于最终采用的元数据扩展和平台加密架构，不能凭当前 SMMPT 规范直接推导出统一标准流程。

## 13.7.5 一个容易忽略的关键细节：SDID 不是全局身份

按照当前 `Smsd` 的架构定义，`mmpt.SDID` 是 Hart-local Identifier。

规范明确指出，不应直接把这个仅在 Hart 本地具有意义的 SDID 用作全局可见 Downstream Transaction 的唯一身份标签。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



例如：

```
Hart 0:
  SDID = 2 -> OP-TEE

Hart 1:
  SDID = 2 -> Another Domain
```

如果下游 Memory Encryption Engine 仅仅依据 `SDID=2` 选择密钥，那么不同 Hart 的请求就可能被错误地关联到同一个安全上下文。

因此实际 SoC 必须有一个可信的、在相应范围内唯一的 Domain/Encryption Context 映射策略。

这是区分“会读取 CSR”与“真正能够设计 SoC 安全机制”的关键细节。

## 13.7.6 当前工程上应该如何使用这部分知识？

我建议将 Metadata Selection 作为独立的 Architecture Interface 设计，而不要让 OP-TEE 的通用 MMU 代码直接依赖尚未定稿的 `Svpams` 编码。

例如，可以先定义平台抽象：

```
enum mem_security_type {
    MEM_SEC_PRIVATE,
    MEM_SEC_GLOBAL_SHARED,
    MEM_SEC_RESTRICTED_SHARED,
};

struct mem_security_context {
    uint64_t global_domain_id;
    uint32_t encryption_context;
    enum mem_security_type type;
};
```

然后把底层实现交给：

```
int platform_set_memory_security(
    uint64_t pa,
    size_t size,
    const struct mem_security_context *ctx);
```

这是参考 API，不能直接替代实际的 Cache、MPT、I/O MPT、Encryption Engine 同步协议。

这种抽象最大的好处是：

未来即使平台从私有 Memory Encryption 方案迁移到正式标准化的元数据机制，OP-TEE 的上层内存管理也不必重新设计。

# 13.8 Attestation：如何证明一个 Supervisor Domain 真的可信？

到这里，我们已经具备了一套相对完整的安全系统：

```
Memory Isolation
DMA Isolation
Interrupt Isolation
Debug / Trace Policy
QoS Isolation
Memory Encryption
```

但现在出现一个完全不同的问题：

如何让远程用户相信这些安全机制真的已经启用，而且运行的软件没有被替换？

这就是 Attestation 要解决的问题。

## 13.8.1 Secure Boot 不等于 Remote Attestation

先区分两个概念。

Secure Boot 解决的问题是：

> 当前设备是否只允许符合信任策略的固件或软件启动？

例如：

```
ROM
  |
  | Verify Signature
  v
Firmware
  |
  | Verify Signature
  v
OpenSBI / RDSM
  |
  | Verify / Measure
  v
OP-TEE or TSM
```

Remote Attestation 解决的问题是：

> 一个远程服务如何验证目标平台或 Workload 的身份、测量状态及相关安全声明？

举一个例子。

远程用户计划向 Confidential VM 提供一份机密数据。

用户需要确认：

- VM 运行的代码是预期版本。
- 平台属于受信任的硬件和固件体系。
- 管理 VM 的 TSM 是可信版本。
- 安全隔离策略满足要求。
- Debug/Trace 状态不会破坏安全承诺。
- 当前 Evidence 不是攻击者重放的旧证据。

Secure Boot 可以作为基础，但无法独立解决全部 Remote Attestation 问题。

## 13.8.2 Attestation 的基本参与者

IETF RATS 定义了 Attester、Verifier、Relying Party 等角色。

逻辑角色图：实际协议可以由 Relying Party 或 Verifier 发起 Challenge，并不要求消息只能沿图示单向传输。

其中：

- Attester： 生成与自身运行环境有关的 Evidence。
- Verifier： 验证签名、证书链、测量值及安全策略。
- Relying Party： 根据 Attestation Result 决定是否信任目标。

RISC-V CoVE 的 Attestation 设计采用了 IETF RATS 模型，并讨论了基于 DICE 的分层证据链。

GitHub



## 13.8.3 为什么 Measurement 必须覆盖整个 TCB？

假设只测量 OP-TEE Binary：

```
Measurement = SHA384(OPTEE_IMAGE)
```

这是否足够？

显然不够。

如果 RDSM 已经被攻击者替换，或者 MPT 初始化存在安全漏洞，OP-TEE Binary 本身再正确，也无法保证隔离。

因此，Attestation 需要覆盖与安全承诺有关的可信计算基。

例如：

```
Hardware Root of Trust
      |
      v
Boot Firmware
      |
      v
OpenSBI / RDSM
      |
      v
TSM / OP-TEE
      |
      v
Confidential Workload
```

其中不同层的测量可以分开维护。

CoVE 文档将整体 TCB 划分为：

| TCB Layer    | 典型内容                                  |
| ------------ | ------------------------------------- |
| Platform TCB | Hardware RoT、M-mode Firmware、SoC 安全功能 |
| TSM TCB      | TEE Security Manager                  |
| TVM TCB      | Confidential VM 的测量页面及配置              |

这意味着 Remote Attestation 不是简单计算一个 Kernel Image 的 SHA-256。

它需要形成能够证明整个信任链的证据。

## 13.8.4 从 Measurement 到 Evidence

一个典型的扩展测量机制是：

\\[ M\_{next} = H(M\_{current}\parallel NewData) \\]

其中：

- \\(M\_{current}\\)：当前 Measurement。
- `NewData`：新的测量输入。
- \\(H\\)：密码学哈希函数。

这样每次扩展都会把新的输入绑定到已有测量状态。

例如：

```
M0 = H(Initial State || Firmware Hash)
M1 = H(M0 || RDSM Hash)
M2 = H(M1 || TSM Hash)
```

这仅是用于理解的示例；实际 CoVE/DICE 测量寄存器和凭据派生关系更加明确，并不要求所有组件被放入同一个线性 Hash 链。

在 DICE 模型中，平台还可以基于设备秘密和测量值派生不同层的 Compound Device Identifier（CDI），并建立硬件信任根支持的签名验证关系。

它的一个重要价值是：不同软件层的身份和密钥能够绑定到它们的测量状态。

## 13.8.5 为什么 Attestation 必须有 Nonce？

假设平台昨天是安全的。

攻击者记录昨天的 Attestation Evidence。

今天平台已经被修改，但攻击者继续把昨天的 Evidence 返回给远程服务。

如果远端只检查签名和软件 Hash，那么旧的有效证据仍可能被接受。

因此需要 Freshness。

常见方法是由验证方提供一个新的 Challenge：

```
Nonce = Random Challenge
```

Attester 必须将其绑定进签名保护的 Evidence 中。

这样 Verifier 就能判断当前收到的 Evidence 是否响应本次请求。

但是需要注意：

Nonce 证明的是证据的新鲜性，不代表设备未来的运行状态永远不会改变。

运行期安全仍然依赖 RDSM/TSM 对安全不变量的持续维护，以及必要时重新证明、撤销信任或更新会话策略。

## 13.8.6 为什么 Debug/Trace 状态必须与 Evidence 绑定？

考虑两份声明：

```
Evidence A:
  Firmware = Trusted
  OP-TEE = Trusted
  External Debug = Disabled
```

```
Evidence B:
  Firmware = Trusted
  OP-TEE = Trusted
  External Debug = Enabled
```

虽然二者的软件 Hash 完全相同，但安全性可能完全不同。

如果 External Debug 允许读取安全内存，那么远程客户不应该仅因 Binary Hash 正确就向该平台提供私钥。

因此 Attestation Policy 可能要求：

```
Debug = Disabled
Trace = Disabled
MPT = Enabled
Memory Encryption = Required
Security Firmware Version >= Minimum
```

这些只是示例策略，具体 Evidence Claim 的编码和是否能得到硬件可信证明，取决于平台实现。

特别要避免一个架构漏洞：

```
Attest while Debug is disabled
        |
        v
Receive customer secret
        |
        v
Enable Debug without invalidating trust
        |
        v
Read customer secret
```

如果平台允许这个流程，就说明 Attestation 状态与安全运行状态之间缺乏足够的绑定。

正确设计应在开启相关 Debug 能力时遵循受信任的授权、状态转换、重新测量或失效策略。

# 13.9 SMMPT 与 CoVE：它们到底是什么关系？

这一节是本章最后一个重要的架构主题。

先明确一个核心观点：

SMMPT 是可以支持 CoVE 的底层物理内存隔离机制之一，但 CoVE 的目标远不止建立多个 S-mode Domain。

## 13.9.1 CoVE 需要解决什么问题？

假设云平台的 Host Hypervisor 是不可信的。

用户希望创建 Confidential VM：

```
Host Hypervisor
    |
    | Creates VM
    v
Confidential VM
```

普通虚拟化模型中，Host 通常能够控制大量 Guest 内存管理状态。

如果用户不信任 Host，那么就需要一个机制：

```
Host can manage resources
but cannot read TVM private memory
```

这涉及两个主要边界：

1. Host 与 TSM 的相互隔离。
2. Host/其他 VM 与 TVM Private Memory 的隔离。

CoVE 将这些需求组织成可信虚拟机的生命周期管理、Guest ABI、Host ABI、内存管理以及 Attestation 等机制。

## 13.9.2 一个基于 Supervisor Domain 的 CoVE 架构

CoVE 的一种 Supervisor Domain 部署模型。TVM 的内部隔离还依赖由可信组件控制的 G-stage 等机制，并非只由 MPT 单独完成。

各组件的职责如下：

| 组件          | 核心责任                                          |
| ----------- | --------------------------------------------- |
| Host        | 不可信资源管理、VM 创建请求和调度协调                          |
| RDSM        | 建立 Supervisor Domain 边界、执行安全 Domain Switching |
| TSM         | Confidential VM 生命周期及安全状态管理                   |
| SMMPT       | Host/TSM 等 Domain 之间的物理访问控制                   |
| G-stage     | TVM Guest Physical Address 相关转换与隔离            |
| I/O MPT     | 保护设备访问的 Domain 物理权限                           |
| Attestation | 对平台、TSM、TVM 的可信声明提供证据                         |

CoVE 不限定必须使用 SMMPT；不同平台可以使用满足安全目标的其他硬件隔离方案。RISC-V CoVE 的公开参考架构也支持不同部署模型。

GitHub+1



## 13.9.3 SMMPT 和 G-stage 为什么不能互相替代？

假设：

```
Host:
  HS-mode

TSM:
  HS-mode, separate Supervisor Domain

TVM:
  VS-mode + VU-mode
```

这里存在两种不同的访问控制需求。

需求一：Host 不能访问 TSM 的物理内存。

可以通过：

```
Host MPT
TSM MPT
```

建立两个 Supervisor Domain 的隔离。

需求二：TVM A 不能访问 TVM B 的内存。

如果两个 TVM 都由一个可信 TSM 管理，则可以由 TSM 建立相应的 Guest 内存转换与访问权限。

例如：

```
TVM A GPA
    |
    | G-stage managed by TSM
    v
TVM A SPA
    |
    | MPT for TSM Domain
    v
Physical Memory
```

因此：

- MPT 可以在 Host/TSM 之间建立较粗的安全域边界。
- G-stage 等机制可以在 TSM 管理的范围内，进一步隔离不同 TVM。

这是一种分层设计。

如果只配置 Host/TSM 的 MPT，却让 Host 依旧控制所有 TVM 的安全敏感 G-stage 映射，那么机密性目标就可能不成立。

如果只使用 G-stage，却没有办法阻止不可信 Host 直接映射或访问其物理页面，也不能建立所需的 Host/TSM 隔离。

## 13.9.4 完整 TVM 生命周期中，SMMPT 在哪里发挥作用？

考虑一条完整路径：

```
Host requests TVM creation
       |
       v
TSM validates request
       |
       v
RDSM enforces domain isolation
       |
       v
Secure memory ownership established
       |
       v
TSM builds protected TVM mappings
       |
       v
TVM measurement and finalization
       |
       v
TVM runs
       |
       v
Attestation
       |
       v
TVM destroy and memory reclaim
```

在这个模型中，SMMPT 的关键价值包括：

创建阶段： 确保 Host 无法访问 TSM 私有内存，并对需要从 Host 转为 Confidential Domain 管理的资源执行合适的物理权限转移。

运行阶段： 随着 Hart 在不同 Domain 间切换，确保各自的 MPT 权限仍然有效。

共享阶段： 在需要共享 Buffer 时，建立明确的授权范围。

销毁阶段： 资源归还给 Host 之前，确保原有 Confidential Data 和安全上下文已经正确清理。

需要强调的是，CoVE 中某个物理页面如何在 RDSM、TSM、Host 之间管理，取决于具体部署模型和 ABI。不能把 Chapter 10 的教学状态机直接认定为 CoVE 已标准化的 Memory Management ABI。

## 13.9.5 CoVE Attestation 的实际接口

在 RISC-V AP-TEE/CoVE 的公开草案中，Guest 可以通过：

```
sbi_covg_get_evidence(...)
```

请求生成 Attestation Evidence。

并且可以通过可选接口：

```
sbi_covg_extend_measurement(...)
```

扩展运行期测量。

这里的 `sbi_covg_get_evidence()` 属于 CoVE Guest ABI 草案，不是 SMMPT 本身的指令或 CSR。

# 13.10 把所有安全机制串起来：完整的威胁模型

到目前为止，我们讨论的机制非常多。

如果只是分别记住它们的定义，很容易再次陷入“每个组件好像都理解，但无法形成完整系统”的困境。

因此我建议从一个安全工程师最重要的工具开始：Threat Model（威胁模型）。

假设我们的攻击者是已经完全控制 Host Linux 的云平台管理员。

他可以：

- 控制 Linux 内核和普通用户态程序。
- 修改 Linux 页表。
- 向设备提交 DMA 请求。
- 配置被授权给 Host 的 MMIO。
- 使用 Host 可访问的性能计数器。
- 尝试触发各种系统中断。
- 试图通过已有接口请求 Debug 或 Trace 权限。

但我们假设他不能直接修改 RDSM，也不能伪造 Hardware Root of Trust 的签名。

对于物理攻击，则需要另行声明攻击者是否能够接触 DRAM、主板总线、封装内部或供电和时钟系统。

### 13.10.1 安全威胁与防御矩阵

| 攻击方式                     | SMMPT 是否足够         | 需要的其他机制                           |
| ------------------------ | ------------------ | --------------------------------- |
| Linux 读取 OP-TEE DDR      | 在完整 CPU 访问路径上可执行隔离 | 正确的 MPT 配置与切换                     |
| 设备 DMA 访问 Secure DDR     | 不足够                | I/O MPT / IOMMU 等                 |
| Linux 接收 Secure IRQ      | 不足够                | Smsdia / AIA 与路由保护                |
| JTAG 读取 Secure Registers | 不足够                | Secure Debug Authorization        |
| Trace 观察秘密相关分支           | 不足够                | Trace 隔离及安全软件实现                   |
| LLC Cache Side-channel   | 不足够                | QoS、分区及其他侧信道缓解                    |
| DRAM 物理窃听                | 不足够                | Memory Encryption                 |
| DRAM 数据篡改/重放             | 不足够                | Memory Integrity / Anti-replay    |
| 伪造可信平台身份                 | 不足够                | Hardware RoT / Attestation        |
| 恶意 Host 导致资源耗尽           | 不能完全阻止             | Resource Quota / Scheduling / QoS |

这张表说明一个很重要的架构思想：

安全性来自多个独立防御机制的组合，而不是一个超级强大的单一机制。

## 13.10.2 重新理解 Trusted Computing Base

在传统 OP-TEE 架构中，我们往往首先关注：

```
Secure World
Non-secure World
```

但当我们进入 RISC-V Supervisor Domain 与 Confidential Computing 架构后，必须关注：

```
What components must remain correct
to preserve workload confidentiality
and integrity?
```

例如，对于一个基于 SMMPT 的 Confidential VM：

```
Hardware Root of Trust
        |
        v
RDSM / M-mode Firmware
        |
        v
SMMPT / I/O MPT / Interrupt Isolation
        |
        v
Trusted TSM
        |
        v
Confidential VM
```

但 TCB 还可能包括：

- 实施内存加密的硬件。
- 执行访问控制的互连。
- Debug Security Controller。
- 与安全声明相关的设备 Firmware。
- Attestation Key 和 Measurement Storage。

这里有一个经常被忽略的事实：

Security Boundary 不一定与 Software Component Boundary 一致。

例如，安全策略由 RDSM 软件制定，但实际 DMA Enforcement 位于 I/O Bridge。

所以你即使能审计完整的 RDSM C 代码，也不能据此保证 DMA 隔离一定正确。

因为硬件设计、RTL、IOMMU 配置和设备接口仍然是信任假设的一部分。

# 13.11 实际工程：设计一个完整的 RISC-V Secure Domain Platform

下面将 Chapter 10–13 的内容整合起来。

## 13.11.1 SoC 硬件条件

假设：

```
RISC-V SoC:
  16 × RV64 Harts

Firmware:
  Hardware RoT
  OpenSBI
  RDSM

Supervisor Software:
  Linux Host
  OP-TEE
  TSM

Memory:
  32 GB DDR

Devices:
  NVMe
  PCIe
  Crypto Engine

Security Hardware:
  MPT
  I/O MPT
  IOMMU
  AIA + Smsdia
  Debug Security
  CBQRI
  Memory Encryption
```

硬件能力是这个设计的前提，并不代表所有 RISC-V 服务器芯片都已经实现这套组合。

## 13.11.2 为每个 Domain 定义安全策略

可以建立一个 RDSM Domain Manifest。

例如：

```
struct rdsm_domain_policy {
    uint32_t domain_id;

    /* Memory isolation */
    uint64_t mpt_root_pa;

    /* Interrupt assignment */
    uint32_t sidn;

    /* QoS isolation */
    uint32_t qrid;
    uint32_t rcid_base;
    uint32_t rcid_count;
    uint32_t mcid_base;
    uint32_t mcid_count;

    /* Platform-specific security */
    uint32_t debug_policy;
    uint32_t trace_policy;
    uint32_t encryption_context;

    /* Security state */
    uint64_t policy_generation;
};
```

这是参考软件结构，不是规范定义的 RDSM 数据结构。

其中 `domain_id` 应为系统软件管理的全局逻辑 Domain Identity，而不能直接假设它等于所有 Hart 上的本地 SDID。

如果使用独立 Hardware Root of Trust，例如 SoC 中的独立 HSM Core，则可以让它负责：

- 验证 Firmware Image。
- 验证 Domain Manifest。
- 管理 Attestation Key。
- 管理与 Memory Encryption 有关的密钥。
- 对 Debug Authorization 进行可信裁决。

RDSM 则负责把这些策略落实到 CPU 和 SoC 运行时状态中。

## 13.11.3 Domain Switch 时到底需要恢复哪些状态？

前面已经学习过：

```
mmpt
msdcfg.SIDN
```

现在增加：

```
QoS Context
Debug/Trace Policy
Crypto-related Context
```

完整的参考状态如下：

| 状态                      | 示例机制                     | 负责的隔离维度       |
| ----------------------- | ------------------------ | ------------- |
| Memory                  | `mmpt`、MPT               | 物理访问          |
| Address Translation     | `satp`、`hgatp`           | Domain 内部地址空间 |
| Interrupt               | `msdcfg.SIDN`、中断 CSRs    | 中断归属          |
| QoS                     | `mnrmcfg`、`msdcfg`       | 资源分配与监控       |
| Debug/Trace             | 独立安全控制状态                 | 调试与跟踪权限       |
| Encryption              | 平台安全上下文                  | 内存数据保护        |
| CPU Architectural State | GPR、FP、Vector、Trap State | 执行状态隔离        |

最重要的是最后一项。

即使 MPT、I/O MPT、QoS 全部正确，如果 Domain Switching 时泄漏 CPU Register 或其他需要隔离的执行状态，仍可能破坏 Confidentiality。

例如：

```
OP-TEE:
  f0 / v0 / General Register
  contains secret-dependent data

RDSM switches to Linux

Linux:
  Unexpectedly observes stale state
```

正确的保存、恢复或清零策略必须覆盖平台支持的相关状态。

还有一些实现相关的微架构状态，例如 Branch Predictor、Cache 和 Speculation State，不能简单地认为切换了 `mmpt` 就自动安全隔离。

## 13.11.4 RDSM 的 Domain Switching 框架

参考伪代码：

```
int rdsm_switch_domain(
    struct domain_ctx *next)
{
    struct domain_ctx *prev =
        rdsm_current_domain();

    /*
     * 1. Establish a trusted switch boundary.
     */
    rdsm_enter_critical_section();

    /*
     * 2. Stop any cross-domain observation
     *    or execution of untrusted state.
     */
    rdsm_apply_switch_debug_policy();
    rdsm_quiesce_sensitive_trace();

    /*
     * 3. Save previous domain context.
     */
    rdsm_save_cpu_context(prev);
    rdsm_save_interrupt_context(prev);
    rdsm_save_qos_context(prev);

    /*
     * 4. Validate target domain state.
     */
    if (!rdsm_validate_domain(next))
        goto fail;

    /*
     * 5. Apply memory and platform context.
     */
    rdsm_install_mpt(next);
    rdsm_install_interrupt_domain(next);
    rdsm_install_qos_context(next);

    /*
     * Platform-dependent:
     * debug/trace security and cryptographic
     * context selection.
     */
    rdsm_install_platform_security(next);

    /*
     * 6. Restore target architectural state.
     */
    rdsm_restore_cpu_context(next);
    rdsm_restore_interrupt_context(next);

    /*
     * 7. Complete required synchronization,
     *    mark target active and resume.
     */
    rdsm_prepare_resume(next);
    rdsm_resume_domain(next);

    __builtin_unreachable();

fail:
    rdsm_enter_safe_failure_state();
    return -1;
}
```

这里特意没有规定所有 CSR、Cache Fence、Debug Controller 和 Encryption Engine 的精确更新指令。

因为这些状态的正确更新顺序与具体实现密切相关，并且某些状态可能要求在更早的入口阶段就被屏蔽。

例如，不能等到执行 `rdsm_quiesce_sensitive_trace()` 时才停止原本已经持续泄漏敏感数据的 Trace Path。

真正的实现必须在架构设计阶段明确安全切换的起点，以及哪些状态允许在不可信上下文仍可观察时发生变化。

### 13.11.5 建议定义一个统一安全不变量

可以将整个 Domain Switch 的目标表达为：

\\[ Resume(D) \Rightarrow \begin{cases} MemoryContext = D\\\ InterruptContext = D\\\ QoSPolicy = Policy(D)\\\ DebugTracePolicy = Policy(D)\\\ ArchitecturalState = State(D) \end{cases} \\]

对于加密相关状态，如果执行路径涉及上下文切换，则还必须满足相应平台的加密和共享内存策略。

这不是规范规定的形式化表达式，而是建议用于设计评审的安全不变量。

它能够帮助我们避免只检查一个 `mmpt` CSR，就宣称整个 Supervisor Domain Switching 已经完成。

# 13.12 工程调试、源码研究和验证实验

本章涉及大量尚未统一到单一成熟开源参考平台中的功能，因此最适合采用分层验证。

## 实验一：安全 Debug Authorization

目标：证明 Linux Debug Access 无法访问 OP-TEE Private State。

测试场景：

```
Hart 0: Linux Domain
Hart 1: OP-TEE Domain

Debug Permission:
  Linux  = Allowed
  OP-TEE = Denied
  RDSM   = Denied
```

建议验证：

| 测试                             | 预期行为    |
| ------------------------------ | ------- |
| Halt Linux Hart                | 按策略允许   |
| Read Linux Registers           | 允许      |
| Read OP-TEE Private DDR        | 拒绝      |
| Halt Protected OP-TEE Context  | 拒绝      |
| Debug Module SBA 访问 Secure DDR | 拒绝      |
| Reset / 重新授权                   | 按安全策略处理 |

如果目标 RTL 或仿真模型尚未支持 External Debug Security，不能用普通 Debug Spec 的行为假装通过这组测试。此时应将其标记为硬件能力缺失，并使用抽象安全控制模型验证策略逻辑。

## 实验二：QoS Side-channel 与资源竞争

目标：验证 RDSM 建立的 QoS Policy 不会被不可信 Domain 越权修改。

测试系统：

```
Linux:
  QRID = 0
  Heavy memory bandwidth workload

OP-TEE:
  QRID = 1
  Secure computation
```

进行三组实验：

| 实验 | 条件                  |
| -- | ------------------- |
| A  | 不进行 QoS 限制          |
| B  | 两个 Domain 使用不同 RCID |
| C  | 使用 QRI 配额与适当的资源分区   |

测量：

- OP-TEE Latency。
- Linux Bandwidth。
- LLC Occupancy。
- QoS Controller Monitoring Counter。
- 不同 Domain 的统计访问权限。
- 配置寄存器越权访问结果。

这里的目标不仅是观察性能改善，还必须验证配置和监控隔离。

例如：

```
Linux attempts:
  Change OP-TEE RCID allocation
```

预期 RDSM 或硬件拒绝。

不要把“性能波动变小”直接作为侧信道已经消除的证据。

## 实验三：Memory Encryption Context Transfer

目标：验证 Memory Ownership 与 Encryption Context 一致。

初始状态：

```
Page P
Owner = Linux
Key   = K1
```

转移后：

```
Page P
Owner = OP-TEE
Key   = K2
```

故意注入：

- 缺少 Cache Synchronization。
- MPT 已切换但 Encryption Context 未切换。
- 旧密文被恢复。
- Integrity Metadata 未更新。
- DMA 使用旧上下文写入。
- 转移失败时页面被错误重新分配。

期望系统以受控方式报告错误或保持隔离，而不是产生静默的数据泄漏。

若硬件没有真实的 Memory Encryption Engine，可以先做软件状态机模拟，不应把软件 XOR 或普通 Buffer 加密示例当作硬件内存加密的验证。

## 实验四：Attestation Policy

目标：验证不安全平台配置不会通过 Remote Attestation。

构造两组 Evidence。

```
Evidence A:
  MPT enabled
  Debug disabled
  Trusted RDSM measurement
  Fresh nonce
```

```
Evidence B:
  MPT enabled
  Debug enabled
  Trusted RDSM measurement
  Fresh nonce
```

即使二者 RDSM Hash 相同，Verifier 也应该能够根据被可信认证的配置声明作出不同的信任判断。

随后增加：

```
Evidence C:
  Previous nonce
  Trusted measurements
```

验证其因 Freshness 不满足而被拒绝。

再增加一个关键攻击实验：

```
1. Attestation succeeds
2. Remote secret released
3. Debug authorization changes
4. Existing session continues
```

检查平台是否具有可信状态转换、重新验证或会话撤销策略。

这是比“证书签名能验过”更有价值的系统级实验。

# 13.14 本章总结：从 Memory Protection 走向 Confidential Computing

本章最值得掌握的，不是增加了多少新的扩展名称，而是建立完整的 SoC 安全思维。

可以把整个架构分成五个层次：

Layer 5 · Attestation

向远程用户证明可信身份、测量和安全配置

Layer 4 · Debug / Trace / QoS Security

约束可观察性、共享资源和运行时安全状态

Layer 3 · Memory Confidentiality & Integrity

抵抗威胁模型内的物理读取、篡改及重放

Layer 2 · Domain Resource Isolation

MPT、I/O MPT、Interrupt Domain 和资源所有权

Layer 1 · Hardware Root of Trust

可信启动、配置授权、测量及密钥信任根

这五层并不是严格的调用顺序，而是帮助理解不同安全能力的逻辑分层。

我希望通过 Chapter 13，真正建立以下几个认识：

第一，SMMPT 不等于完整的 SoC Security。

它建立重要的物理内存访问边界，但 Debug、Trace、QoS、物理内存攻击和 Attestation 都需要单独处理。

第二，安全设计必须同时考虑 Control Plane 与 Data Plane。

例如，QoS Controller 执行资源限制，但谁能够配置 QoS、读取统计信息，同样决定这个功能是否安全。

第三，Isolation 与 Attestation 是两种不同但互补的能力。

Isolation 在本地实施安全策略；Attestation 让外部主体能够验证与这些策略有关的可信声明。

第四，Memory Ownership Transfer 不只是 MPT Entry 的修改。

在涉及内存加密的系统中，必须进一步管理 Encryption Context、缓存、数据完整性、旧事务及页面生命周期。

第五，CoVE 不是 SMMPT 的同义词。

CoVE 将物理隔离、可信虚拟化管理、Workload 生命周期和 Attestation 结合起来。SMMPT 可以成为其中的关键硬件基础，但无法独立完成整个机密计算系统。

至此，Part III：System-Level Resource Isolation（Chapter 10–13）全部完成。

`Hardware RoT → M-mode Firmware → MPT Initialization → RDSM → Linux/OP-TEE Supervisor Domain`

这样我们将不再只讨论安全机制是什么，而是深入研究第一张 MPT 在哪里创建、由谁创建，什么时候可以安全进入第一个 S-mode Domain，以及 OpenSBI 和 OP-TEE 的代码应当如何协作。
