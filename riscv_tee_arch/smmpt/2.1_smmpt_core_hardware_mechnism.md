# Chapter 07 — SMMPT、MMU、PMP 之间的协同与异常

核心目标：能够独立分析一次访存的全部权限检查，并准确判断 Fault 产生的位置及安全影响。

## 7.1 为什么必须同时理解 MMU、PMP 和 SMMPT？

假设我们有一个 RISC-V SoC，运行如下两个 Supervisor Domain：

| 属性             | Domain A                | Domain B                |
| -------------- | ----------------------- | ----------------------- |
| 软件             | Linux                   | OP-TEE                  |
| Privilege Mode | S-mode                  | S-mode                  |
| SDID（示例）       | 1                       | 2                       |
| 私有内存           | 0x8000_0000–0x8FFF_FFFF | 0x9000_0000–0x90FF_FFFF |
| 安全属性           | Non-secure              | Secure                  |

其中 Secure/Non-secure 是软件安全域的概念，并非 RISC-V 自带的两种 S-mode。

假设 Linux 试图读取 OP-TEE 的 Private Memory：

```
uint64_t value =
    *(volatile uint64_t *)0xffffffe000100000UL;
```

请注意，这里的 C 指针表示 Linux 使用的 Virtual Address。假设 Linux 自己建立了一条页表映射：

```
Linux VA: 0xffffffe000100000
                |
                | Linux-controlled page table
                v
Physical Address: 0x90000000
                |
                v
OP-TEE Private Memory
```

这时候有一个很关键的问题：

Linux 已经拥有 S-mode 最高的软件权限，并且能够修改自己的页表，为什么仍然不能读取 0x90000000？

答案就是：Linux 的 MMU 页表和 SMMPT 的 MPT 分属于不同的权限控制层。

### 7.1.1 三种机制维护的是不同的安全边界

逻辑权限检查模型。实际微架构可以并行检查或缓存结果，并不要求严格按照图示顺序逐级串行执行。

三者的分工如下：

MMU：

决定当前虚拟地址能够映射到哪个物理地址，以及当前软件上下文是否有权使用该映射。

SMMPT：

决定当前 Supervisor Domain 是否有权访问这个物理地址。

PMP/Smepmp：

通过 M-mode 管理的物理区域权限，限制低特权级别的访问，并根据配置影响 M-mode 本身。

因此，我们可以建立一个概念公式：

\\[ Allow=MMU\_{allow}\land MPT\_{allow}\land PMP\_{allow} \\]

这里暂时忽略 PMA、IOMMU 等其他机制。

这个公式不是规范规定的硬件流水线，而是访问控制结果的逻辑表达。

### 7.1.2 为什么这比单独使用 MMU 安全？

Linux 可以修改：

- `satp`
- 自己的 Page Table
- PTE 中的 `R/W/X`
- 对应映射的 Virtual Address

但是，Linux 无权直接修改 M-mode 控制的 `mmpt`，也不应该能够修改 MPT 的物理内容。

因此：

```
Linux PTE: R=1, W=1, X=0
          |
          v
VA → PA 0x90000000
          |
          v
Linux Domain MPT: XWR=000
          |
          v
Access Denied
```

即使 Linux 通过修改页表绕过了自己的 MMU 管理策略，仍然无法绕过 SMMPT 的 Domain 边界。

这种隔离的安全性，建立在 RDSM 可信、MPT 不可被 Domain 擅自修改、全部相关访问路径被硬件保护等前提之上。

## 7.2 从一条 Load 指令深入硬件权限检查

现在我们沿着真实指令执行路径分析。

```
ld t0, 0(a0)
```

假设：

```
Privilege       = S-mode
Current Domain  = Linux
SDID            = 1
satp.MODE       = Sv39
mmpt.MODE       = Smmpt43

a0              = 0xffffffc000100000
```

Linux Page Table 将这个 VA 映射到 PA `0x90000000`。

### Stage 1：MMU 进行地址转换

Sv39 使用三级页表完成 VA → PA 转换。

```
VA
 |
 +-- VPN[2]
 |
 +-- VPN[1]
 |
 +-- VPN[0]
 |
 +-- Page Offset
```

MMU 依次检查页表项的有效性、访问权限和其他约束。

假设：

```
PTE.V = 1
PTE.R = 1
PTE.W = 1
PTE.X = 0
```

本次 `ld` 是 Load 操作，因此通过了 MMU 的读取权限检查。

最终得到：

```
PA = 0x90000000
```

但这一步并不意味着访问已经被允许。

### Stage 2：SMMPT 检查 Domain 的物理访问权限

当前 Hart 的 `mmpt` 指向 Linux Domain 的 MPT。

```
mmpt.SDID = 1
mmpt.MODE = Smmpt43
mmpt.PPN  = Linux MPT Root PPN
```

SMMPT 使用物理地址 `0x90000000` 查询 Linux 的 MPT。

假设最终找到的权限是：

```
XWR = 000
```

表示禁止任何访问。

由于 Load 需要 `R=1`，因此 SMMPT 拒绝访问。

结果为：

```
Load Access Fault
```

规范规定 MPT 权限违反以对应原始访问类型的 Access Fault 报告，且 MPT 访问违规进入 M-mode RDSM。

GitHub+1



### Stage 3：陷入 M-mode RDSM

在典型实现中，RDSM 需要取得故障上下文：

```
Faulting Hart
Current Domain / SDID
Original Privilege Mode
Faulting PC
Exception Cause
Faulting Address Information
```

随后执行策略：

- 拒绝非法访问。
- 记录安全审计事件。
- 判断是否属于预期内的 Fault。
- 必要时终止或重置对应 Domain。
- 视软件 ABI 将故障报告给上层。

需要特别注意：不能因为出现 Access Fault，就简单地在 RDSM 里面自动为目标 PA 增加访问权限。

这会把安全权限控制机制变成可以被恶意软件试探、逐步突破的动态授权接口。

## 7.3 Page Fault 与 Access Fault 到底有什么区别？

这是实际调试中经常混淆的问题。

| Fault                    | 典型原因                 | Exception Code |
| ------------------------ | -------------------- | -------------- |
| Instruction Access Fault | 指令取址违反物理访问限制         | 1              |
| Load Access Fault        | Load 违反物理访问限制        | 5              |
| Store/AMO Access Fault   | Store/AMO 违反物理访问限制   | 7              |
| Instruction Page Fault   | 指令地址翻译或页表权限失败        | 12             |
| Load Page Fault          | Load 的页表权限或转换失败      | 13             |
| Store/AMO Page Fault     | Store/AMO 的页表权限或转换失败 | 15             |

这些是 RISC-V 标准同步异常编码，不是专门为 SMMPT 新增的一组 Exception Code。

如果 Linux 读取 `0x90000000`：

场景 A：Linux MMU 页表中的 R=0，且不存在其他允许读取的特殊条件。

可以产生 Load Page Fault。

场景 B：Linux 页表 R=1，但 Linux Domain 的 MPTE.R=0。

产生 Load Access Fault。

场景 C：MMU 与 MPT 都允许，但 PMP 拒绝访问目标 PA。

产生 Load Access Fault。

因此：

看到 Load Access Fault，并不能立即断定就是 SMMPT 问题。

必须进一步区分 PMP、PMA、MPT Walk 和最终物理地址访问。

更深入的一点是：如果多个保护条件同时存在问题，实际异常结果还要考虑架构规定的检查优先级、隐式访存及具体执行路径，不能仅靠上面的逻辑图推断哪一个故障一定先被观察到。

## 7.4 MPT Page Walk 本身又如何受到保护？

这是一个很值得深入的架构问题。

我们知道 MMU Page Walk 需要从内存读取 PTE，而 MPT Page Walk 也需要从内存读取 MPTE。

假设 MPT 存储在：

```
MPT Root PA = 0x81000000
```

当 SMMPT 查询这个 MPT 时，硬件会发起隐式内存读取。

这里要区分两种访问：

| 访问                          | 发起上下文                 | 保护方式                |
| --------------------------- | --------------------- | ------------------- |
| Linux 显式读取 MPT 所在地址         | S-mode / Linux Domain | Linux MPT、PMP/PMA 等 |
| SMMPT Hardware Walk 读取 MPTE | 隐式 M-mode 访问          | PMP/Smepmp、PMA 等    |

规范明确规定：MPT Walk 对 MPTE 的隐式读取按照 M-mode 的 PMP/Smepmp 权限进行检查，字节序受 `mstatus.MBE` 控制。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub+1



这个设计很重要，因为不能要求 MPT 在读取自己的权限表之前，先通过同一套 MPT 检查，否则容易产生递归依赖。

但这里有一个新的安全要求：

Root Domain 必须保证 MPT 数据结构所在物理内存无法被不可信 Domain 修改。

否则 Linux 即使无法修改 `mmpt` CSR，也可能通过普通内存 Store 修改 MPTE，最终破坏 Domain 隔离。

因此 RDSM 至少需要确保：

1. MPT 页只由受信任的 M-mode 软件管理。
2. 不可信 Domain 的 MPT 对 MPT 页设置禁止写入，通常也禁止读取。
3. MPT Walk 本身能通过 M-mode 的 PMA/PMP 检查。
4. MPT 分配器绝不能把仍在使用的 MPT 页重新分配给 Linux。

## 7.5 SMMPT 与 Hypervisor G-stage 的关系

现在引入 RISC-V H-extension。

典型虚拟化路径：

```
Guest Virtual Address (GVA)
            |
            v
VS-stage Translation
            |
            v
Guest Physical Address (GPA)
            |
            v
G-stage Translation
            |
            v
Supervisor Physical Address (SPA)
            |
            v
MPT / PMP Protection
```

这里有三种不同权限控制：

- VS-stage 决定 Guest 虚拟地址如何转换。
- G-stage 决定 Hypervisor 管理下的 GPA 如何转换到 SPA。
- MPT 决定当前 Supervisor Domain 对该 SPA 有没有访问权。

### 7.5.1 为什么 Hypervisor 无法直接绕过 MPT？

考虑两个 Domain：

```
Host Domain:
    Linux + KVM
    SDID = 1

Trusted Domain:
    Confidential VM / Trusted OS
    SDID = 2
```

假设 Host Hypervisor 修改自己的 G-stage Page Table：

```
GPA 0x10000000
     |
     v
SPA 0x90000000
```

其中 `0x90000000` 属于 Trusted Domain。

即使 G-stage 映射本身允许访问，Host Domain 的 MPT 仍然可以拒绝访问。

因此，Hypervisor 控制 G-stage 并不等于能够访问所有物理内存。

这是在 Confidential Computing 场景中非常重要的架构能力。

### 7.5.2 更深一步：G-stage Page Table 也可能受到 MPT 检查

假设 CPU 正在进行 G-stage Translation。

硬件需要读取 G-stage PTE，它本身也会形成隐式内存访问。

规范对 VS-stage / G-stage Page Table Walk 的 MPT 检查作出了规定：对页表的读取或写入，按相应隐式 Load/Store 进行 MPT 权限检查；但如果因此出现异常，报告的异常类型仍对应最初的指令访问、Load 或 Store/AMO。

这意味着：

即使最终目标数据页是可访问的，如果翻译过程中需要读取的页表内存没有正确授权，依然可能失败。

这类问题在 Firmware Bring-up 中特别容易被误判为普通 Page Table 构造错误。

## 7.6 `MPRV`、`MXR` 与权限检查中的特殊情况

### 7.6.1 M-mode 执行代码就一定能绕过 MPT 吗？

不一定，要考虑 Effective Privilege Mode。

通常，M-mode 执行的内存访问不会受到当前 MPT 的权限限制。

但是 RISC-V 有 `mstatus.MPRV` 机制，可以让某些 M-mode Load/Store 按 `MPP` 指定的有效权限级别进行访问。

SMMPT 规范明确规定：只要 Effective Privilege Mode 不是 M-mode，`mmpt` 就处于有效状态。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



因此，当：

```
Current Privilege  = M
mstatus.MPRV       = 1
mstatus.MPP        = S
```

对应的数据访问就不能简单地当作普通 M-mode 访问处理。

这对 Firmware 中使用 MPRV 访问 Supervisor Buffer 的实现非常重要。

不过 RDSM 自身的可信操作必须严格管理 `MPRV`，不能以错误的 Effective Privilege Mode 修改 MPT 或安全内存。

### 7.6.2 `MXR` 是否能够改变 MPTE 权限？

不能。

`MXR` 可以影响虚拟内存页表中 Execute-only 页面是否可用于读取，但不能让 MPT 中的 Execute-only 页面变成 Readable 页面。

例如：

```
PTE.X   = 1
PTE.R   = 0
MXR     = 1

MPTE.X  = 1
MPTE.R  = 0
```

即使 MMU 层可能允许该 Load，MPT 仍然拒绝读取。

规范明确规定 MPT 的 XWR 权限不受 `MXR` 或 `HLVX` 改写。

## 7.7 MMIO 是否受到 SMMPT 保护？

答案是：对于受 SMMPT 检查覆盖的 Hart 物理访问路径，MMIO 也可以受到 MPT 保护。

假设 UART 的 MMIO Base Address 是：

```
UART0 = 0x84000000
```

并且 Linux、OP-TEE 分别拥有不同的 Domain。

RDSM 可以为各 Domain 配置不同的 MPT 权限：

| 地址                 | Linux Domain | OP-TEE Domain |
| ------------------ | ------------ | ------------- |
| UART0 MMIO         | R/W          | No Access     |
| Secure Crypto MMIO | No Access    | R/W           |
| Shared Mailbox     | R/W          | R/W           |

这样 Linux 可以直接访问 UART，但不能访问 Secure Crypto Engine 的寄存器空间。

不过还要注意以下问题：

CPU MPT 检查不等于完整的 I/O 安全隔离。

设备 DMA、IOMMU 自身的访存、异步总线 Master 等必须通过适当的 I/O 保护路径处理，不能假设它们天然继承 CPU 上的 MPT 状态。

这会在 Chapter 11 单独深入。

## 7.8 SMMPT Fault 如何定位？

以实际工程调试为例。

假设 Linux 中执行：

```
ld t0, 0(a0)
```

引发 Load Access Fault。

RDSM 的 M-mode Trap Handler 应记录：

```
/* 示意：运行在 M-mode 的 trap handler */
struct mpt_fault_report {
    unsigned long hartid;
    unsigned long mepc;
    unsigned long mcause;
    unsigned long mtval;
    unsigned long mstatus;
    unsigned long mmpt;
};
```

其中：

- `mepc`：发生异常的指令地址。
- `mcause`：异常类型。
- `mtval`：如果实现提供有效信息，通常可能包含故障虚拟地址，不能假定它就是最终 PA。
- `mstatus`：进入 Trap 前的状态信息。
- `mmpt`：当前 Domain ID 和 MPT 配置。

特别强调：`mcause=5` 只说明 Load Access Fault，并不天然说明是 MPT、PMP 还是 PMA 违规。

如果需要精确区分故障来源，RDSM 可以结合保存的页表状态重建翻译过程、检查 MPTE/PMP，并读取平台额外的硬件故障状态寄存器（如果有）。

不要把事后软件重建的结果误认为硬件一定报告的原始故障原因。

### 推荐 Debug 流程

```
Access Fault
     |
     v
Check mcause
     |
     +-- Page Fault?
     |       |
     |       +-- Inspect satp / PTE
     |       +-- Inspect hgatp / G-stage
     |
     +-- Access Fault?
             |
             +-- Inspect PMA / PMP
             |
             +-- Reconstruct VA → PA
             |
             +-- Inspect mmpt / MPT
             |
             +-- Inspect implicit table accesses
             |
             +-- Check MMIO / Platform Fault Status
```

如果使用 TRACE32 或底层硬件调试器，需要进一步验证 CPU 执行时的实际 CSR Context，而不是仅依据 Linux 日志中的异常地址。

# Chapter 08 — MPT Cache、Fence 与多 Hart 同步

核心目标：掌握 MPT 更新后的可见性与时序约束，能够设计跨 Hart 权限撤销协议，避免安全域之间的越权窗口。

## 8.1 为什么修改了 MPTE，硬件不一定立即使用新权限？

理解这一章，首先要回到一个非常基本的 CPU 设计问题：

如果每次访问内存都必须重新遍历完整 MPT，性能会怎样？

假设 CPU 执行：

```
ld t0, 0(a0)
ld t1, 8(a0)
ld t2, 16(a0)
ld t3, 24(a0)
```

这四条 Load 指令大概率访问同一个物理页面。

假设 SMMPT 使用三级 MPT，如果每次 Load 都需要重新从内存读取三个 MPTE，那么仅仅为了确定权限，就可能引入大量额外访存。

因此，实际微架构通常会缓存 MPT Walk 的结果。

注意规范并不要求硬件必须实现某一种具体结构。它可以采用独立的 MPT Permission Cache，也可以与其他地址转换缓存进行集成。

我们可以把 CPU 内部的相关缓存理解为：

| 缓存                   | 缓存内容               | 主要加速目标          |
| -------------------- | ------------------ | --------------- |
| TLB                  | VA/GPA 与 PA 的转换结果  | MMU Translation |
| Page Walk Cache      | 虚拟内存页表的中间信息        | Page Table Walk |
| MPT Permission Cache | PA 对应的 Domain 访问权限 | MPT Lookup      |
| MPT Walk Cache       | MPT 中间层查询结果        | MPT Table Walk  |
| Data Cache           | 程序实际访问的数据          | Load/Store      |

以上是逻辑分类，物理硬件未必具有五种彼此独立的 Cache。

### 8.1.1 第一次 Load

```
CPU Load
    |
    v
MMU Translation
    |
    v
MPT Permission Cache Lookup
    |
    +-- Miss
          |
          v
       MPT Walk
          |
          v
       XWR = 011
          |
          v
       Cache Permission
          |
          v
       Load Allowed
```

### 8.1.2 第二次 Load

```
CPU Load
    |
    v
MPT Permission Cache
    |
    +-- Hit: XWR = 011
          |
          v
       Load Allowed
```

这很好地提升了性能。

但它引出了一个安全问题：

假设 RDSM 已经把权限从 `011` 修改为 `000`，而某个 Hart 的权限缓存仍然保存着 `011`。

此时，内存中的 MPTE 已经禁止访问，但 Hart 仍可能使用旧权限完成访问。

这正是 Fence 和 Invalidation 机制需要解决的问题。

## 8.2 一个非常重要的概念：Store 完成不等于 MPT 权限生效

考虑如下时序：

```
Time     MPT in DDR           Hart 1 MPT Cache

T0       XWR = 011            XWR = 011
T1       RDSM Store XWR=000   XWR = 011
T2       DDR has XWR=000      XWR = 011
T3       Hart 1 Load          May use XWR=011
```

这里必须区分三个事件：

事件 A：MPT Store

RDSM 写入新的 MPTE。

事件 B：Memory Visibility

新 MPTE 对相关的 Hart 可见。

事件 C：MPT Cache Synchronization

缓存的旧权限不再能够被未来的受保护访问使用。

这三个事件不是同一件事情。

单纯的 `fence rw,rw` 不能替代 MPT Cache Invalidation。

而只在 Hart 0 上执行 MPT Fence，也不意味着 Hart 1 的旧缓存自动失效。

这里的本质与 MMU 更新页表后需要进行 TLB 同步很相似，只是同步对象不同。

## 8.3 `MFENCE.PA`：SMMPT 的关键同步指令

SMMPT 定义了 `MFENCE.PA`，用于同步内存中 MPT 的修改与当前 Hart 随后的保护表查询。

它只能在 M-mode 执行。

指令形式：

```
mfence.pa rs1, rs2
```

两个寄存器分别表示：

- `rs1`：物理地址选择参数。
- `rs2`：Supervisor Domain Identifier 选择参数。

需要牢记：这是 PA（Physical Address），而不是 VA。

### 8.3.1 四种操作范围

| rs1    | rs2    | 同步范围                    |
| ------ | ------ | ----------------------- |
| `x0`   | `x0`   | 所有 Domain、所有相关 MPT      |
| `x0`   | 非 `x0` | 指定 SDID 的 MPT           |
| 非 `x0` | `x0`   | 指定 PA 的 Leaf 权限，所有 SDID |
| 非 `x0` | 非 `x0` | 指定 PA、指定 SDID 的 Leaf 权限 |

一个容易忽视的细节：

这里的“是否为 `x0`”是按照 寄存器编号判断，而不是简单地判断寄存器内数值是否等于零。

例如，如果希望针对 SDID 0 进行指定域同步，需要把数值 0 装入一个非 `x0` 寄存器，而不是直接使用 `x0`，否则将表示所有 Domain。

规范还允许简化实现忽略地址、SDID 参数，直接执行更大范围的同步。因此指令参数是允许硬件优化的范围提示，并非保证实际操作只影响这一范围。

GitHub



### 8.3.2 汇编示例

假设 RDSM 更新了：

```
Target PA = 0x90000000
SDID      = 1
```

示意代码：

```
li t0, 0x90000000
li t1, 1

mfence.pa t0, t1
```

这条指令的语义是同步当前 Hart 对该 PA、该 SDID 的相关 MPT 访问。

如果修改的是 MPT 的上级 Non-leaf MPTE，影响可能覆盖大量物理地址。此时不应想当然地使用单个 Leaf 地址的细粒度 Fence；在没有严格证明覆盖范围正确之前，应采用 Domain-wide 或 Global Fence。

例如：

```
li t1, 1

mfence.pa x0, t1
```

同步当前 Hart 与指定 SDID 有关的整个 MPT 范围。

### 8.3.3 `MFENCE.PA` 不是什么？

这点值得单独强调。

它不是：

- 对所有 Hart 的自动广播。
- 通用 Data Cache Clean 指令。
- 所有设备 DMA 的同步指令。
- `SFENCE.VMA` 的简单别名。
- 强制完成全部已发起内存事务的通用机制。

它的规范核心保证是：当前 Hart 上，已经对该 Hart 可见的先前 Store，按照规定顺序先于后续隐式 MPT 读取。

因此，实现安全权限撤销时，还需要考虑跨 Hart Memory Ordering，以及未完成访问的收敛问题。

## 8.4 `MINVAL.PA`：为什么还要一种更细粒度的指令？

假设 RDSM 要回收 1000 个页面。

最简单的方法可能是：

```
Update Page 0
MFENCE.PA

Update Page 1
MFENCE.PA

...

Update Page 999
MFENCE.PA
```

这种方案有明显的性能问题。

每修改一项就执行一次完整 Fence，可能引入大量重复同步开销。

因此，规范提供了 `MINVAL.PA`，用于批处理失效操作。

它与 `SFENCE.W.INVAL`、`SFENCE.INVAL.IR` 配合使用。

### 8.4.1 正确的批量同步模型

```
sfence.w.inval

minval.pa t0, t1
minval.pa t2, t1
minval.pa t3, t1

sfence.inval.ir
```

三个阶段的含义是：

1. `SFENCE.W.INVAL`：对此前已经可见的 Store 建立所要求的排序。
2. `MINVAL.PA`：指定需要失效的 MPT 权限缓存范围。
3. `SFENCE.INVAL.IR`：确保这些失效操作先于后续隐式 MPT 查询。

规范规定：在同一个 Hart 上按这一顺序执行时，可以取得与相应 `MFENCE.PA` 等效的排序效果。`MINVAL.PA` 自身并不独立提供完整的 Fence 语义。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



这与 Linux MMU/TLB 中使用批量失效来降低开销的思想相似。

### 8.4.2 为什么不能只执行 `MINVAL.PA`？

考虑：

```
sd t0, 0(a0)       # Update MPTE

minval.pa t1, t2   # Invalidate
```

问题在于：缺少与前后隐式查询关联的完整排序保证。

因此不能只依靠单条 `MINVAL.PA` 就认为 MPTE 的 Store 与后续权限检查已经正确同步。

### 8.4.3 实际工程中的选择

| 场景                | 推荐方式                                               |
| ----------------- | -------------------------------------------------- |
| 单页权限修改            | `MFENCE.PA`                                        |
| 一批 Leaf MPTE 修改   | `SFENCE.W.INVAL` + `MINVAL.PA` + `SFENCE.INVAL.IR` |
| 大规模结构性修改          | Domain-wide / Global Fence                         |
| 多 Hart 修改         | 各相关 Hart 分别完成本地同步                                  |
| DMA / I/O Checker | 另外执行对应的 I/O MPT 同步                                 |

这些是推荐的软件设计策略，而不是说所有实现必须采用完全相同的同步粒度。

## 8.5 什么时候可以省略 MPT Fence？

这是规范中很有价值、也容易被过度推广的优化。

对于 MPTE 从：

```
Invalid → Valid
```

规范允许一个特殊的可见性保证：

当把 `V` 从 0 改为 1 的 Store 已对某 Hart 可见后，后续隐式 MPT 访问最终必须在一个有界时间内观察到这项改变。

因此，某些纯 `Invalid → Valid` 场景可以省略相应 MPT Fence，代价是短时间内仍可能发生多余的 Access Fault。

但反向变化：

```
Valid → Invalid
```

不能套用这一优化。

原因非常简单：

Invalid → Valid 允许一段时间的保守拒绝；Valid → Invalid 如果还允许旧权限，可能直接造成越权访问。

同样，修改已有有效 MPTE 的 XWR 权限、修改 Non-leaf 指针、复用 SDID 等操作，也不能简单归类为上述免 Fence 场景。

这一区别在安全软件中很重要。对于有严格完成时限要求的 API，即使是授权操作，也通常倾向于显式同步，避免接口已经返回成功但目标 Hart 仍然观察到旧拒绝状态。

## 8.6 多 Hart 环境：为什么 Local Fence 远远不够？

现在构建一个真实的 SMP 场景。

假设 SoC 有 4 个 Hart：

```
Hart 0: Linux Domain
Hart 1: Linux Domain
Hart 2: Linux Domain
Hart 3: OP-TEE Domain
```

Linux Domain 的 SDID 在各 Hart 上可能被设置为相同值，但架构只保证 SDID 是 Hart-local Identifier，并不保证这个数值在全系统唯一。

为了便于案例分析，我们假设各 Linux Hart 都使用 SDID 1。

当前 Linux 对物理页面 `0x90000000` 拥有 Read 权限。

RDSM 准备撤销该权限，并把此页面转交给 OP-TEE。

### 8.6.1 错误的实现

```
Hart 0 / RDSM                 Hart 1 / Linux

Update MPTE R=0
        |
MFENCE.PA
        |
        |                     Old MPT Cache: R=1
        |                              |
        |                              v
        |                         Linux Load
        |                              |
        |                              v
        |                         Still Allowed?
```

这里存在安全漏洞风险，因为 Hart 0 的本地 Fence 没有自动同步 Hart 1。

### 8.6.2 正确的系统级思路

设计者需要同时解决三个问题：

第一：阻止仍然拥有旧权限的 Hart 继续发起访问。

例如让相关 Hart 进入受信任的 M-mode RDSM 执行路径。

第二：使 MPT 修改对这些 Hart 可见，并在每个 Hart 上执行正确的本地 MPT 同步。

第三：确认旧 Domain 的相关访问已经收敛，才允许内存转交给新 Domain。

这里不能只依赖 Linux 自己响应一个普通软件通知，因为 Linux 可能已经被攻击者控制。

RDSM 需要依靠可信的 Hart 控制机制。

## 8.7 设计一个跨 Hart MPT Shootdown Protocol

下面给出一个比较稳健的参考方案。

参考设计流程，并非规范规定的固定顺序。设备隔离、在途事务的排空，以及处理器同步需要根据 SoC 的实际硬件契约细化；在具体实现中可能需要把 DMA 停止提前到权限撤销之前。

### 8.7.1 阶段一：进入 Transition 状态

RDSM 将目标页面的 Ownership 状态设为：

```
OWNER_TRANSITION
```

禁止其他 Domain 在这期间重新授权、释放或迁移该页面。

此时不能仅仅依靠一把普通 Spinlock 保证安全，因为锁只能串行化遵守锁协议的软件，不能阻止恶意 Domain 继续访问物理地址。

### 8.7.2 阶段二：Quiesce 相关 Hart

RDSM 让所有可能执行旧 Domain 的 Hart 进入受信任的同步点。

例如：

```
Hart 0 → M-mode
Hart 1 → M-mode
Hart 2 → M-mode
```

应确认这些 Hart 已不再执行旧 Domain 中可能访问目标页面的指令，并按平台契约处理在途访问。

同时需要阻止这些 Hart 在撤销完成前重新进入旧 Domain。

### 8.7.3 阶段三：修改 MPTE

由可信 M-mode Software 更新目标 MPTE。

```
Old: XWR = 011
New: XWR = 000
```

如果一项 MPTE 包含多个页面的权限，更新必须保证同一 MPTE 中其他页面的授权位保持正确。

### 8.7.4 阶段四：Remote MPT Synchronization

通过可信的同步机制让相关 Hart 执行本地 `MFENCE.PA`，或者对应的批量失效序列。

示意：

```
/* 设计伪代码，并非 OpenSBI 现有 API */
for_each_affected_hart(hart) {
    rdsm_remote_mpt_sync(hart, pa, domain);
}

rdsm_wait_all_sync_complete();
```

具体实现还必须建立如下关系：

```
MPTE Store
   happens-before
Remote Hart observes updated MPT
   happens-before
Remote synchronization completion
   happens-before
Old domain can run again
```

这里的 `happens-before` 是我们希望建立的系统同步关系，不是说一个普通 C 写操作和一个 IPI 自动具备全部这些保证。

需要结合 RISC-V Memory Model、CPU Cache Coherency、Release/Acquire、Fence 及 IPI Completion 机制仔细实现。

### 8.7.5 阶段五：DMA 与 I/O MPT 同步

即使所有 CPU Hart 已经完成 Fence，设备仍可能具有独立的权限缓存。

因此，如果目标内存可以被设备访问，还必须：

- 阻止旧设备发起新的越权 DMA。
- 完成 IOMMU/I/O MPT Checker 所需的权限同步。
- 处理 In-flight DMA Transaction。
- 确认设备不会继续写入目标内存。

I/O MPT Checker 的规范定义了单独的 `MPTINVAL` 操作，用于同步其缓存的 MPT 信息。这不是在 Hart 上执行 `MFENCE.PA` 就能自动替代的。

GitHub



### 8.7.6 阶段六：清理并重新分配

当旧 Domain 已经不可能访问该页面时，RDSM 才能安全地清除数据，再授权新 Domain。

完整状态变化应当类似：

```
LINUX_OWNED
    |
    v
TRANSITION
    |
    v
REVOKED_AND_QUIESCED
    |
    v
SCRUBBED
    |
    v
TEE_OWNED
```

这个过程的核心安全不变量是：

\\[ OldDomainAccess = false \\]

必须先成立，才能让新 Domain 开始依赖该页面的私有性。

## 8.8 SDID、ASID、VMID 与缓存标签的关系

很多人容易把 SDID 和 ASID 混淆。

实际上，它们属于不同层次。

| ID   | 主要标识对象                       |
| ---- | ---------------------------- |
| ASID | 虚拟地址空间                       |
| VMID | 虚拟机的 G-stage 地址空间            |
| SDID | 当前 Hart 上的 Supervisor Domain |

SMMPT 规范将 SDID 纳入相关地址转换标识的有效上下文。

概念上：

```
Effective ASID = (SDID, ASID)

Effective VMID = (SDID, VMID)
```

它并不意味着硬件一定把两者直接按位拼接成寄存器值，而是说明缓存和相关 Fence 不能把属于不同 SDID 的相同 ASID/VMID 错误地当成相同地址空间。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



### 8.8.1 SDID Reuse 的风险

假设：

```
Old Domain A:
SDID = 3

Domain A destroyed

New Domain B:
SDID = 3
```

此时，如果 Hart 还缓存着旧 Domain A 的相关权限、地址翻译和其他 Domain-tagged 状态，新 Domain B 可能观察到错误的旧状态。

因此 SDID Reuse 不是单纯修改 `mmpt.SDID`。

RDSM 必须在适当的时机同步 MPT 及其他按 SDID 标记的缓存和上下文。

一个关键区别是：SDID 的架构作用域是 Hart-local，所以不能直接假定“全平台 SDID 3”就是同一个安全域。

## 8.9 MPT Fence、TLB Fence、Data Cache 操作不能相互替代

| 操作                     | 主要用途                     |
| ---------------------- | ------------------------ |
| `SFENCE.VMA`           | 同步 S-stage 虚拟地址转换相关信息    |
| `HFENCE.GVMA`          | 同步 G-stage 转换相关信息        |
| `MFENCE.PA`            | 同步 MPT 更改与 MPT 隐式查询      |
| `MINVAL.PA`            | 支持批量 MPT 失效              |
| `FENCE`                | 对指定类别的内存/I/O 操作建立排序      |
| `FENCE.I`              | 同步指令获取与此前的数据写入（本地作用域）    |
| Cache Clean/Invalidate | 根据平台机制处理数据缓存状态           |
| I/O `MPTINVAL`         | 同步 I/O MPT Checker 的权限缓存 |

例如，一个 RDSM 在更新 Linux Domain 的页表和 MPT 时，不能认为执行一次 `SFENCE.VMA` 就一定同时清除了 MPT 权限缓存。

同样，更新一块共享代码内存时，也可能同时涉及 Data Cache、Instruction Fetch、MMU 和 MPT 多种同步问题。

它们服务于不同的安全与一致性目标。

## 8.10 本章工程实验与故障注入

推荐做四组实验。

实验 A：单 Hart 权限撤销

先允许访问页面，再修改 MPTE 为 No Access。观察执行 `MFENCE.PA` 前后的结果。由于硬件可能提前观察新权限，不能把“Fence 前仍可访问”当作必然结果。

实验 B：多 Hart 旧权限窗口

两个 Hart 访问同一页。Hart 0 修改 MPT，Hart 1 不执行同步。用于检验参考实现是否正确模拟旧权限缓存，随后加入 Shootdown。

实验 C：SDID Reuse

创建 Domain A、建立缓存状态、销毁 A，再以相同 SDID 创建 B，检查是否遗留权限或转换状态。

实验 D：批量权限修改

比较 1000 次单独 Fence 与批量 `MINVAL.PA` 序列的开销。

重点收集：

```
Update Count
Fence Count
IPI Count
Maximum Synchronization Latency
MPT Cache Miss
Page Walk Count
Total Revoke Latency
```

# Chapter 09 — MPT 管理算法与性能设计

核心目标：从软件架构师视角设计 MPT Manager，掌握表项创建、权限修改、内存分配、并发同步、性能优化以及安全事务管理。

前面两个章节，我们已经解决了两个核心问题：

- Chapter 07：SMMPT 如何判断是否允许访问？
- Chapter 08：MPT 修改之后，如何确保所有相关 Hart 正确观察到新权限？

现在进入第三个问题：

一个实际操作系统或者 Firmware，应该如何设计和管理 MPT？

这是从理解 Specification 迈向实际工程实现的重要转折点。

## 9.1 从硬件机制转换到软件管理

先建立一个基本认知：

SMMPT Specification 定义硬件能够如何查询和解释 MPT，但不会替 Firmware 设计完整的内存分配器、Ownership Manager 或 Domain Lifecycle Manager。

就像 RISC-V Sv39 定义了页表结构，但不会规定 Linux 必须采用哪套内存管理算法一样。

对于 SMMPT，软件需要设计：

```
                    RDSM
                      |
          +-----------+-----------+
          |                       |
    Domain Manager          Memory Manager
          |                       |
    Domain Lifecycle       Memory Ownership
          |                       |
          +-----------+-----------+
                      |
                MPT Manager
                      |
          +-----------+-----------+
          |           |           |
      Table Alloc   MPTE Ops   Fence/Shootdown
          |           |           |
          +-----------+-----------+
                      |
                MPT in DRAM
                      |
                 MPT Checker
```

其中 MPT Manager 最重要的职责有四个：

1. 将高层安全策略转换为 MPTE 权限。
2. 维护 MPT 的完整性和生命周期。
3. 处理权限更新时的同步和并发。
4. 确保软件状态与硬件实际权限一致。

## 9.2 MPT 应该如何组织？

假设我们使用 RV64 `Smmpt43` 模式。

根据规范：

- 支持 43-bit Supervisor Physical Address。
- 使用三级 MPT。
- 每个 MPTE 为 8 Bytes。
- 每个 MPT Table 为 4KB，包含 512 个 MPTE。
- 一个最低层普通 Leaf MPTE 可以分别管理 16 个 4KB 页面。

这意味着最细粒度的物理内存权限是 4KB，但并不是每个 4KB 页面都需要一个独立的 8-byte MPTE。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



### 9.2.1 物理地址拆分

对于 Smmpt43：

43-bit Supervisor Physical Address

pn[2]

42:34

pn[1]

33:25

pn[0]

24:16

range offset

15:0

每级 pn 为 9 bit；range offset 的高 4 bit 选择 Leaf MPTE 中的 16 个 XWR 权限槽，低 12 bit 是 4KB Page Offset。

可以用以下代码提取：

```
#define MPT_INDEX_MASK 0x1ffUL

static unsigned mpt_index_l2(uint64_t pa)
{
    return (pa >> 34) & MPT_INDEX_MASK;
}

static unsigned mpt_index_l1(uint64_t pa)
{
    return (pa >> 25) & MPT_INDEX_MASK;
}

static unsigned mpt_index_l0(uint64_t pa)
{
    return (pa >> 16) & MPT_INDEX_MASK;
}

static unsigned mpt_leaf_slot(uint64_t pa)
{
    return (pa >> 12) & 0xf;
}
```

因此，寻找一个 4KB 页的权限，并不是“三级页表 + 一个独立的 4KB PTE”。

更准确地说，是：

```
PA
 |
 +-- pn[2] → Root MPTE
 |               |
 |               v
 +-- pn[1] → Level-1 MPTE
 |               |
 |               v
 +-- pn[0] → Level-0 Leaf MPTE
 |               |
 |               v
 +-- slot   → XWR[0..15]
                 |
                 v
            Allow / Deny
```

当然，任何中间级 MPTE 也可能直接是 Leaf，允许更大粒度的权限映射。

## 9.3 MPT 的内存开销到底有多大？

这可以通过实际计算建立量化认识。

假设：

```
Physical Memory = 1 GiB
Page Size       = 4 KiB
Leaf MPTE       = 8 Bytes
Pages per MPTE  = 16
```

那么：

\\[ Pages=\frac{1GiB}{4KiB}=262144 \\]

每个 Leaf MPTE 管理 16 个 Page：

\\[ LeafEntries=\frac{262144}{16}=16384 \\]

因此：

\\[ LeafMemory=16384\times8=128KiB \\]

由于一个 MPT Table 为 4KB，Leaf Table 的数量为：

\\[ LeafTables=\frac{128KiB}{4KiB}=32 \\]

对于一个 1GiB 连续且对齐的物理区域，若始终使用最低层 Leaf，还需要一个 Root Table 和一个中间层 Table：

\\[ Total=128KiB+4KiB+4KiB \\]

Smmpt43 · 1GiB · 全部采用最低层 Leaf

# 136 KiB

约占受保护内存的 0.013%

Leaf Tables

128 KiB

Level-1 Table

4 KiB

Root Table

4 KiB

这个结果说明：MPT 的空间开销通常可以控制得很小。

但不能因此得出“MPT 一定比 PMP 更快”的结论。

PMP 使用有限的寄存器匹配资源，而 MPT 需要 Table Walk 和权限缓存。

对于频繁更新权限的系统，真正需要关注的是：

- MPT Cache Miss Rate。
- Table Walk Latency。
- Domain Switch Cost。
- Fence / Shootdown Cost。
- 动态表结构维护成本。

此外，136KiB 是上述特定映射形态的计算结果，不代表任意稀疏地址空间或所有 MPT 模式的固定开销。

## 9.4 如何利用 Large Leaf 和 NAPOT 优化 MPT？

Smmpt43 允许在不同级别使用 Leaf MPTE。

其权限粒度如下：

| Leaf Level | 单个 XWR 权限槽覆盖范围 |
| ---------- | -------------- |
| Level 0    | 4KB            |
| Level 1    | 2MB            |
| Level 2    | 1GB            |

注意：一个普通 Leaf MPTE 仍然包含 16 个 XWR 槽，因此单个 MPTE 能覆盖比表中单个权限槽更大的范围。

### 9.4.1 举例：一段连续的 Linux 内存

假设：

```
Physical Memory:
0x80000000 - 0xBFFFFFFF

Size = 1 GiB
Owner = Linux
Permission = RW
```

因为这段区域具有统一的访问策略，所以不必一定创建完整的最低层 MPT。

可以考虑在更高层使用 Leaf MPTE 编码这段区域的权限。

这样能节省下级 MPT Table 的内存及潜在 Walk 成本。

### 9.4.2 NAPOT 优化解决什么问题？

NAPOT 是 Naturally Aligned Power-of-Two 的缩写。

它允许连续、对齐的权限区域使用有利于硬件缓存合并的表示方式。

在 Smmpt43 中，规范定义了 `G=4` 的 NAPOT 编码，用于帮助硬件将 2MB 或 1GB 权限区域缓存为一个更大的权限缓存项。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



这里要区分两个优化目标：

大粒度 Leaf： 减少下级表结构，降低表存储和 Walk 成本。

NAPOT： 让硬件有机会将连续权限区域合并缓存，提高 Permission Cache 的利用率。

二者有关联，但不是完全相同的优化机制。

### 9.4.3 为什么不能所有内存都用 Large Leaf？

假设原来整个 1GB 区域属于 Linux，但现在需要从中取出一个 4KB 页面交给 OP-TEE。

原来的统一权限策略：

```
1 GiB: Linux RW
```

需要变成：

```
前面区域: Linux RW

目标 4KB: Linux No Access
           OP-TEE RW

后面区域: Linux RW
```

这时候高层 Leaf 无法再用一个粗粒度授权描述目标页面与相邻页面的不同权限。

MPT Manager 必须将相关映射细分，建立更低级别的 MPT。

这就是 MPT Split 操作。

## 9.5 MPT Split 与 Merge：管理算法的核心

### 9.5.1 Split 操作

假设 Root Leaf 对某个物理范围定义了大粒度权限。

现在需要改变其中一小部分页面的权限。

安全实现需要：

1. 读取原 Leaf 的全部权限信息。
2. 分配并初始化必要的下级 MPT Table。
3. 将原 Leaf 描述的所有子区域权限正确展开到新表。
4. 修改目标子区域的权限。
5. 在可信同步点将原 Leaf 替换为 Non-leaf。
6. 执行所需的 MPT 同步。
7. 释放旧结构（如果确实不再引用）。

最重要的细节是第三步。

不能只填充新分配的目标页面，而遗漏原先大 Leaf 中的其他授权。

因为一个 Root Leaf 可能包含 16 个不同的 1GB 权限槽。如果拆分这个 Root Leaf，需要保持它覆盖的其他区域的原有策略，或者经过显式策略批准改变它们。

### 9.5.2 为什么 Split 过程需要事务性？

考虑以下错误实现：

```
Old Root Leaf: Linux RW
       |
       v
Replace Root Leaf with new Non-leaf
       |
       v
Start populating children
```

在建立完整的新子表之前，硬件可能已经开始根据新的 Non-leaf 进行 Walk。

这可能导致：

- 无效 MPTE。
- 意外的 Access Fault。
- 临时出现不正确权限。
- 并发 Hart 观察到不一致结构。

因此，推荐先准备完整的新表，再在受控的同步阶段发布。

### 9.5.3 Merge 操作

当一段区域恢复为统一权限时，可以考虑反向操作：

```
Many small MPTEs
         |
         v
Same effective policy?
         |
         +-- No → Keep small mappings
         |
         +-- Yes
               |
               v
         Create larger Leaf
               |
               v
         Synchronize
               |
               v
         Reclaim old tables
```

在 Merge 时，不能简单因为所有页面当前都是 `RW` 就合并。

还要确认：

- 全部区域的所有者与权限策略一致。
- 无正在进行的 Memory Transfer。
- 没有要求保持独立粒度的安全资源。
- 合并不会引入原来不存在的访问许可。
- 不再有 Hart 或 I/O Checker 使用即将释放的旧 MPT Table。

## 9.6 如何设计 MPT Manager 的软件数据结构？

现在开始进入类似 Firmware Source Code Design 的层面。

以下是用于设计讨论的参考结构，不是现有 OpenSBI 主线中的具体定义。

### 9.6.1 Domain 结构

```
struct mpt_domain {
    uint64_t domain_id;

    paddr_t root_mpt_pa;

    uint64_t generation;

    struct spinlock lock;

    struct hart_mask resident_harts;

    struct mpt_allocator *allocator;
};
```

逐个分析。

`domain_id`

由 RDSM 使用的系统级逻辑 Domain Identifier。

它不一定等于每个 Hart 的硬件 SDID。

`root_mpt_pa`

当前 Domain 使用的 MPT Root Physical Address。

`generation`

用于区分不同版本的权限状态。

例如，当 MPTE 发生更新后：

```
generation = 101 → 102
```

这个字段由软件设计，用于辅助同步确认、调试和生命周期管理，并不是 SMMPT 规定的 CSR 字段。

`lock`

串行化对当前 MPT 数据结构的并发修改。

`resident_harts`

记录可能持有当前 Domain 相关上下文和缓存状态的 Hart。

这里不能简单理解成“正在运行该 Domain 的 Hart”，因为刚刚切走的 Hart 仍然可能保留缓存。

### 9.6.2 内存 Ownership 结构

单独维护 Ownership 信息：

```
enum mem_owner {
    MEM_FREE,
    MEM_ROOT,
    MEM_LINUX,
    MEM_TEE,
    MEM_SHARED,
    MEM_TRANSITION,
};

struct mem_region {
    paddr_t base;
    size_t size;

    enum mem_owner owner;

    uint32_t flags;
    uint32_t refcount;
};
```

一个很重要的设计原则：

Ownership Database 不应该直接等同于 MPT。

原因是二者表达的信息不同：

```
Ownership:
Who is allowed to authorize future changes?

MPT:
What access is currently allowed by hardware?
```

例如一块 Shared Memory：

```
Owner = Root / TEE

Linux MPT:
    R/W

OP-TEE MPT:
    R/W
```

MPT 中显示两个 Domain 都能够读写，但不代表 Linux 有权决定这块内存未来的 Ownership。

因此，RDSM 必须维护独立于硬件权限表的安全策略和资源所有权状态。

## 9.7 如何修改一个最低层 MPTE？

这部分值得深入到位操作。

在 Smmpt43 中，一个普通的 64-bit Leaf MPTE 包含 16 组 XWR 权限。

每一组占用 3 bit。

对于第 `slot` 个页面：

\\[ Shift=8+3\times slot \\]

对应权限掩码：

\\[ Mask=0x7 \ll Shift \\]

假设我们只希望修改一个 4KB 页的权限。

可以使用下面的参考实现：

```
#define MPTE_V             (1ULL << 0)
#define MPTE_L             (1ULL << 1)
#define MPTE_N             (1ULL << 2)

#define MPTE_XWR_MASK      0x7ULL

static uint64_t
mpt_set_leaf_page_perm(uint64_t old,
                       unsigned int slot,
                       unsigned int xwr)
{
    unsigned int shift;
    uint64_t mask;

    if (slot >= 16)
        return old; /* Real code must report an error. */

    shift = 8 + 3 * slot;
    mask = MPTE_XWR_MASK << shift;

    return (old & ~mask) |
           (((uint64_t)xwr & 0x7) << shift);
}
```

这个函数说明了一个十分重要的事实：

修改一个 4KB 页的权限，可能需要更新包含其他 15 个页面权限的同一个 64-bit MPTE。

这意味着 MPT Manager 不能只考虑权限正确性，还必须考虑 Read-Modify-Write 并发。

### 9.7.1 并发写入问题

假设 Hart 0 和 Hart 1 都由可信 RDSM 代码管理同一个 MPTE。

```
Original MPTE:
XWR[0] = RW
XWR[1] = RW
```

Hart 0 想修改 `XWR[0]`。

Hart 1 想修改 `XWR[1]`。

如果两者都读取原始 MPTE，分别修改，再写回整条 64-bit MPTE，就可能发生 Lost Update。

因此需要：

- 通过锁串行化 MPTE 更新；或者
- 使用经过严格设计的原子 Read-Modify-Write 机制。

如果使用 I/O MPT Checker，还必须满足规范对其观察 MPTE 原子更新的要求。RV64 平台应特别关注对齐的 64-bit MPTE Store 是否符合系统的原子性与内存一致性契约。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



### 9.7.2 还必须验证 MPTE 的合法性

上面的函数只演示位操作，不是完整权限管理函数。

正式实现至少需要检查：

- MPTE 是否 Valid。
- 是否确实是 Non-NAPOT Leaf。
- Slot 是否在有效范围内。
- XWR 编码是否合法。
- 是否设置了 Reserved Bits。
- 当前 Domain 是否有权修改该区域。
- 该权限变化是否需要撤销和同步。
- 修改过程中是否存在并发访问者。

例如 `XWR=010` 和 `XWR=110` 在当前规范中属于保留编码，不能随意用作有效权限。

## 9.8 设计完整的 `mpt_update_permission()` 事务

现在把前面所有知识串联起来。

假设希望实现：

```
mpt_update_permission(domain,
                      pa,
                      size,
                      permission);
```

从调用接口上看，这只是一个很简单的函数。

但真正的实现其实包含多个阶段。

```
Validate Request
       |
       v
Check Domain Ownership
       |
       v
Lock / Reserve Region
       |
       v
Quiesce Affected Execution
       |
       v
Allocate or Split MPT
       |
       v
Update MPTEs
       |
       v
Synchronize All Affected Harts
       |
       v
Synchronize I/O Access
       |
       v
Update Software Ownership State
       |
       v
Release / Commit
```

### 9.8.1 参考伪代码

```
/*
 * Design pseudocode:
 * Not an existing OpenSBI/OP-TEE implementation.
 */
int mpt_change_permission(struct mpt_domain *dom,
                          paddr_t pa,
                          size_t size,
                          unsigned int perm)
{
    struct mpt_transaction tx;
    int rc;

    rc = validate_mpt_request(dom, pa, size, perm);
    if (rc)
        return rc;

    rc = begin_mpt_transaction(&tx, dom, pa, size);
    if (rc)
        return rc;

    rc = quiesce_affected_users(&tx);
    if (rc)
        goto abort;

    rc = prepare_mpt_changes(&tx, perm);
    if (rc)
        goto abort;

    rc = publish_mpt_changes(&tx);
    if (rc)
        goto recovery;

    rc = sync_affected_harts(&tx);
    if (rc)
        goto recovery;

    rc = sync_affected_io(&tx);
    if (rc)
        goto recovery;

    rc = verify_transition_complete(&tx);
    if (rc)
        goto recovery;

    commit_mpt_transaction(&tx);
    return 0;

recovery:
    /*
     * May have externally visible partial changes.
     * Keep users blocked; recover under trusted control.
     */
    enter_mpt_recovery(&tx);
    return rc;

abort:
    rollback_unpublished_changes(&tx);
    return rc;
}
```

这段伪代码要重点理解几个地方。

### 9.8.2 为什么区分 Abort 和 Recovery？

如果权限修改尚未发布到硬件可见的 MPT，通常还有机会安全地释放新分配的 Table，并恢复到修改前状态。

但如果 MPTE 已经发布，甚至部分 Hart 已经完成同步，就不能简单通过：

```
return -EINVAL;
```

结束操作。

因为此时硬件与软件可能已经处于部分修改状态。

例如：

```
Hart 0: New Permission

Hart 1: New Permission

Hart 2: Old Permission

Ownership DB: TRANSITION
```

如果函数直接返回并允许 Linux 继续运行，就可能出现严重问题。

因此，正式实现必须有明确的 Recovery Protocol。

可以选择：

- 维持隔离，继续重试同步。
- 进入安全故障状态并隔离相关 Domain。
- 按经过验证的流程回滚权限。
- 对于无法安全恢复的系统级错误执行受控重置。

安全性优先于业务可用性。

另外，不应在持有可能被远端 Trap Handler 获取的锁时无限等待 Remote IPI ACK，否则可能产生死锁。实际实现通常需要将锁保护的数据结构操作与跨 Hart 等待阶段仔细分离。

## 9.9 性能分析：MPT 系统的开销主要来自哪里？

假设现在进行两种操作。

场景 A：Linux 连续访问 1GB 内存。

权限基本不发生变化。

场景 B：Linux 和 OP-TEE 每秒进行大量 4KB 内存授权和撤销。

权限频繁发生变化。

虽然两种场景都访问 SMMPT，但是性能特征可能完全不同。

### 9.9.1 一个简单的性能模型

定义：

\\[ T\_{total}=T\_{lookup}+T\_{update}+T\_{sync}+T\_{transfer} \\]

其中：

- \\(T\_{lookup}\\)：MPT 查询及 Cache Miss 开销。
- \\(T\_{update}\\)：MPTE 更新和 Table 管理开销。
- \\(T\_{sync}\\)：Fence、IPI 和 Shootdown 开销。
- \\(T\_{transfer}\\)：在途访问收敛、DMA 同步、清理内存等开销。

在稳定访问场景中，`T_lookup` 可能是主要关注点。

在频繁授权和撤销场景中，`T_sync` 和 `T_transfer` 可能成为瓶颈。

因此，不能只优化 MPT Walk，而忽视整个 Memory Ownership Transfer Protocol。

### 9.9.2 优化策略一：尽量减少需要动态修改的物理页面

对于频繁共享的数据，可以考虑预先分配固定的 Shared Memory Pool。

例如 OP-TEE 与 Linux 的 RPC Shared Memory。

优点：

- 减少每次调用的 MPT 更新。
- 减少跨 Hart Fence。
- 降低动态 Split/Merge 开销。

但代价是：预先授权的 Shared Memory 暴露面更大，需要通过软件协议、Buffer Validation 和生命周期管理控制风险。

### 9.9.3 优化策略二：Batching

假设一次调用需要回收 256 个 Page。

不推荐：

```
Update 1 Page → Remote Fence
Update 1 Page → Remote Fence
...
```

更合理：

```
Quiesce
   |
Update 256 Pages
   |
Batch Invalidation
   |
Single Synchronization Phase
   |
Resume
```

这样可以降低 IPI 和同步次数。

但必须保证 Batch 内所有页面在提交完成前不会被旧 Domain 非法使用，也不能提前让新 Domain 依赖尚未完成的权限转换。

### 9.9.4 优化策略三：选择合适的 MPT Granularity

对于：

```
Static Linux Memory
Static OP-TEE Private Memory
```

可以优先考虑大粒度映射。

对于：

```
Dynamic Shared Memory
Per-page Memory Transfer
Guest Memory Donation
```

则可以采用较细粒度的 MPTE。

这和 Linux MMU 管理中 Huge Page 与 Small Page 的取舍非常相似，但多了跨 Domain 物理隔离的安全要求。

### 9.9.5 优化策略四：减少无意义的 Domain Switch Fence

不应该假定每次从 Linux Domain 切换到 OP-TEE Domain，都必须无条件清除所有 MPT 权限缓存。

如果两个 Domain 的 MPT 结构都没有变化，并且硬件正确地使用 SDID 区分缓存上下文，就可以探索保留有效缓存状态。

但当：

- MPTE 修改。
- Root MPT 变化。
- SDID 复用。
- 缓存上下文可能发生混淆。

就必须按照规范实施相应同步。

这也是为何 Domain Context Management 和 MPT Management 不应该完全独立设计。

## 9.10 将 MPT Manager 集成到 OpenSBI / OP-TEE

这一部分先给出合理的软件架构，真正的代码对接将在 Part IV 展开。

推荐将核心权限管理放在受信任的 M-mode RDSM 中。

```bash
                    Linux
                      |
                SBI / Trusted ABI
                      |
                      v
                 M-mode RDSM
                      |
        +-------------+-------------+
        |             |             |
   Domain Manager  MPT Manager  I/O Manager
        |             |             |
        +-------------+-------------+
                      |
                Hardware MPT
                      |
             +--------+--------+
             |                 |
         Linux SD          OP-TEE SD
```

其中 OP-TEE 仍然可以维护自己的：

- Virtual Memory Layout。
- Secure Page Table。
- TA Memory Allocation。
- Trusted Thread Context。
- Shared Memory Metadata。

但涉及跨 Domain 的物理内存授权，需要由具有对应权限的 RDSM 控制并执行。

### 9.10.1 一个推荐的模块接口

```cpp
/* Conceptual APIs, not upstream APIs. */

int rdsm_domain_create(...);

int rdsm_domain_destroy(...);

int rdsm_mpt_map(...);

int rdsm_mpt_unmap(...);

int rdsm_mpt_set_perm(...);

int rdsm_mpt_revoke(...);

int rdsm_mpt_sync(...);

int rdsm_memory_transfer(...);
```

这里的 `rdsm_memory_transfer()` 不应该只是调用一次 `rdsm_mpt_set_perm()`。

因为真正的 Memory Transfer 涉及：

```
Authorization
    +
Ownership
    +
Memory Protection
    +
Concurrency Control
    +
Synchronization
    +
Data Sanitization
```

它是一个高级安全事务，而不是简单的寄存器配置操作。

## 最值得反复研究的三个关键问题

第一，MMU 与 MPT 的关系。Linux 能够修改自己的 Page Table，却无法仅靠修改 Page Table 突破物理 Domain 边界。这是 Supervisor Domain Isolation 的架构基础。

第二，Permission Revocation 的完成条件。在 DDR 中更新 MPTE 只是第一步，必须进一步处理缓存可见性、跨 Hart 同步、在途访问和设备 DMA。这是 SMMPT 实现中最容易引入隐蔽安全漏洞的部分。

第三，MPT Manager 与 Ownership Manager 的分离。硬件权限描述的是当前能够做什么，而安全策略描述的是谁可以决定这些权限。这两个概念必须分开设计。

对于后续的 OP-TEE 移植而言，最值得深入的不是再增加几种 MPTE 编码，而是从一块 4KB 内存的完整生命周期入手：

`Linux-owned → Revoke → Quiesce → Scrub → OP-TEE-owned → Share → Revoke → Reclaim`

沿着这条路径，把 RDSM、OpenSBI、MPT、Fence、SMP、DMA 和 OP-TEE 的实现串联起来。

接下来进入 Part III 时，就可以从 CPU 核内部的权限保护，扩展到真正的 SoC 级安全隔离：Memory Ownership、IOMMU、I/O MPT Checker、中断以及 Confidential Computing。 这也是让 SMMPT 从一个 CPU 架构特性发展成可落地的 TEE 安全方案的关键一步。
