# RISC-V CoVE 深度教程：从 Host ECALL 到 TSM、G-stage 和 TVM

## 1. 先建立完整的执行模型

这次我们不再孤立地介绍 CoVE 的组件，而是跟踪一次真实的执行场景：

Linux/KVM Host 已经创建好一个 TVM，现在要将 TVM 的 vCPU 调度到某个 RISC-V Hart 上执行。

我们关心的不只是“调用哪个接口”，而是整个过程中：

- CPU 的 Privilege Mode 如何变化？
- Host 与 TSM 的 Supervisor Domain 如何切换？
- M-mode 的 RDSM 保存和恢复哪些寄存器？
- `mmpt`、`satp`、`hgatp` 分别由谁管理？
- TVM 如何通过 `sret` 进入 VS-mode？
- TVM 发生 Trap 后如何回到 Host？
- 为什么 Host 不能通过修改 G-stage 页表读取 TVM 内存？

为了让这个过程具体可分析，我们采用 RV64 + H-extension + Supervisor Domain Access Protection（SDAP/SmMTT） 的参考模型。

这不是所有 CoVE 平台唯一允许的部署方式。RISC-V 官方发布的 Supervisor Domain 白皮书明确介绍了 Host 与可信安全管理组件运行在不同 Supervisor Domain、由 M-mode RDSM 负责安全切换的设计。

### 1.1 完整架构

同一个物理 Hart 上的三层执行环境

Host Domain

Linux/KVM

HS-mode

Normal VMs

VS/VU-mode

Confidential Domain

TSM

HS-mode

TVM / Guest Linux

VS/VU-mode

通过 M-mode 受控切换

RDSM / TSM-driver · M-mode

Trap Routing · Context Switch · SDID/MPT · Security Policy

RISC-V Hardware

CSR · H-extension · MMU · MPT Checker · PMP

这张图里有一个非常重要的事实：

Host 与 TSM 在软件特权等级上是平级的。真正使它们隔离的，是它们所属的 Supervisor Domain 以及相应的硬件内存保护。

### 1.2 一次完整的运行路径

```
                       Hart 0

① Host Linux/KVM                     HS-mode
      │
      │ sbi_covh_run_tvm_vcpu()
      │ ecall
      ▼
② M-mode RDSM                         M-mode
      │
      ├── 保存 Host Supervisor Context
      ├── 检查调用是否合法
      ├── 激活 Confidential Domain
      ├── 恢复 TSM Supervisor Context
      │
      │ mret
      ▼
③ TSM                                 HS-mode
      │
      ├── 查询 TVM/vCPU State
      ├── 配置 Guest G-stage
      ├── 恢复 VS CSR
      ├── 恢复 Guest GPR
      │
      │ sret
      ▼
④ TVM Linux                           VS-mode
      │
      ├── 执行 Guest Kernel
      ├── Stage-1 + G-stage Translation
      ├── MPT Permission Check
      │
      │ Trap / VM Exit
      ▼
⑤ TSM                                 HS-mode
      │
      ├── 保存 Guest State
      ├── 分析 Trap
      ├── 生成安全的 Exit Information
      │
      │ ecall
      ▼
⑥ M-mode RDSM                         M-mode
      │
      ├── 保存 TSM Context
      ├── 恢复 Host Domain
      ├── 恢复 Host Context
      │
      │ mret
      ▼
⑦ Host Linux/KVM                      HS-mode
```

这是一条架构级参考执行路径，不是某个已发布版本 TSM 的逐指令 Trace。不同 CoVE 部署模型与版本可以改变具体的 Trap/ABI 路由。

这里有三个需要先记住的关键点。

第一，`ecall` 不等于 Domain Switch。

`ecall` 只触发异常。真正的 Domain Switch 必须由受信任的 M-mode 组件修改安全状态并完成上下文切换。

第二，`mret` 不等于进入 Confidential VM。

第一次 `mret` 只是从 RDSM 返回 TSM 所在的 HS-mode。

随后由 TSM 使用虚拟化机制进入 TVM 的 VS-mode。

第三，G-stage 与 MPT 负责两种不同的安全边界。

```
G-stage
    TVM A ↔ TVM B 的隔离

MPT
    Host Domain ↔ Confidential Domain 的隔离
```

这也是下面所有细节的核心。

## 2. 第一阶段：Host Linux 触发 ECALL

假设 Host 当前正在运行：

```
Hart 0
    Privilege = HS
    Domain    = HOST
    PC        = Host KVM code
```

并且已经存在一个 TVM：

```
struct tvm {
    uint64_t id;
    uint64_t memory_size;
    unsigned int nr_vcpus;
};
```

这里的结构体是教学示例，不是 CoVE 规范定义的 C 结构。

KVM 需要执行：

```
run_tvm_vcpu(tvm_id, vcpu_id);
```

在 CoVE ABI 草案中，`sbi_covh_run_tvm_vcpu()` 是对应的 Host 侧运行接口名称。

### 2.1 SBI 的调用约定

普通 RISC-V SBI 调用使用如下寄存器约定：

| Register  | 用途               |
| --------- | ---------------- |
| `a0`–`a5` | 参数               |
| `a6`      | SBI Function ID  |
| `a7`      | SBI Extension ID |
| `ecall`   | 触发 SBI 调用        |
| 返回 `a0`   | Error Code       |
| 返回 `a1`   | Return Value     |

可以抽象成：

```
# 教学示意，不固定 CoVE ABI 参数编码

mv   a0, s0             # TVM identifier
mv   a1, s1             # vCPU identifier

li   a6, COVH_RUN_FID
li   a7, SBI_EXT_COVH

ecall
```

这里的 `COVH_RUN_FID`、`SBI_EXT_COVH` 是符号占位符；对应常量及参数必须以所选版本的 CoVE 规范为准。

### 2.2 执行 `ecall` 时，CPU 实际做了什么？

假设 Host 正在 HS-mode 运行：

```
PC = 0x8020_1000
Privilege = S/HS
```

并执行：

```
ecall
```

如果配置为由 M-mode 接收该异常，硬件会进行如下状态更新：

```
mcause = 9
mepc   = 0x80201000
mstatus.MPP = S
PC     = mtvec 指向的 Trap Handler
Privilege = M
```

其中：

```
mcause = 9
```

表示 Environment Call from S-mode。

这里特别注意：

`mepc` 保存的是产生异常的 `ecall` 指令地址，而不是下一条指令地址。

所以如果 RDSM 将来要正常返回，就必须使保存的返回 PC 指向 `ecall` 后面的指令。

普通 32-bit `ecall` 指令长度为 4 字节，因此概念上：

```
host_resume_pc = mepc + 4;
```

当然，是否在本次跨域处理后立即回到调用者，由具体 ABI 的同步/异步执行语义决定。

### 2.3 `mstatus` 在这一刻起什么作用？

对于这个 HS → M 的 Trap：

```
Before:
    Privilege = HS

After:
    Privilege = M
```

相关 `mstatus` 字段包括：

| 字段     | 作用                                       |
| ------ | ---------------------------------------- |
| `MPP`  | Trap 前的 Privilege Mode                   |
| `MPIE` | 保存 Trap 前 M-mode interrupt enable 状态     |
| `MIE`  | M-mode 当前 interrupt enable               |
| `MPV`  | H-extension 下记录特定 Trap 前的虚拟化状态，供 MRET 使用 |

对于从 HS-mode 进入 M-mode 的场景：

```
MPP = S
MPV = 0
```

因为 Host HS-mode 对应的是 `V=0` 的 Supervisor Mode。

此时还有另一个关键寄存器：

```
csrr t0, mtvec
```

它决定 M-mode Trap Handler 的入口。

不过 `mtvec` 只控制 Trap 路由入口，并不负责 Domain 切换。

### 2.4 什么时候才真正进入 RDSM？

这里可以用一个十分重要的区分：

```
Hardware Trap Entry
        ↓
M-mode Trap Handler
        ↓
SBI Extension Dispatch
        ↓
RDSM validates request
        ↓
Domain Switch
```

因此，不能把它简化成：

```
ecall → TSM
```

中间必须有可信的 M-mode 控制逻辑。

2025 年 RISC-V 官方白皮书也是将 RDSM 定义为管理 Supervisor Domain 之间隔离和转换的 M-mode 软件组件。

## 3. 第二阶段：M-mode RDSM 保存 Host Context

现在 CPU 已经进入 M-mode。

我们假设：

```
mcause = 9
mepc   = Host ECALL PC
mtvec  = RDSM Trap Vector
```

CPU 已经完成了硬件规定的 Trap Entry，但它不会自动保存全部通用寄存器，也不会自动保存 Host 的所有 Supervisor CSR。

这些都是 M-mode Firmware 要做的工作。

### 3.1 第一个问题：RDSM 使用谁的 Stack？

这与你之前研究 OpenSBI `mscratch` 时遇到的问题完全一样。

进入 Trap 时：

```
sp = Host Kernel Stack
```

如果 RDSM 直接使用这个 Stack：

```
sd ra, 0(sp)
```

就会把自己的执行状态写进不可信 Host 的内存。

更严重的是，Host 可以恶意配置这个 Stack Pointer。

所以 RDSM 必须使用受保护的 M-mode Stack。

一个常见设计是将 `mscratch` 与每个 Hart 的 M-mode Trap Context 关联。

例如：

```
# 教学示意：仅表示 Stack 切换思想
# 不是完整、安全可运行的 Trap Entry

csrrw sp, mscratch, sp
```

逐条理解这条指令：

```
Original:

sp       = Host SP
mscratch = RDSM Stack Pointer

After csrrw:

sp       = RDSM Stack Pointer
mscratch = Host SP
```

但实际实现还必须处理：

- 嵌套 M-mode Trap。
- Trap Entry 最早期的寄存器保存。
- `mscratch` 对不同来源 Trap 的约定。
- Host 与 TVM 切换时的上下文归属。
- Trap Handler 运行时使用的可信存储区域。

因此不能只复制上面的单条指令就当作完整实现。

### 3.2 RDSM 应该保存哪些 Host CSR？

首先看 HS-mode 运行所依赖的主要寄存器。

| 分类             | 关键 CSR                    | 作用              |
| -------------- | ------------------------- | --------------- |
| Trap           | `stvec`                   | HS Trap Vector  |
| Trap           | `sepc`                    | HS Exception PC |
| Trap           | `scause`、`stval`          | HS Trap 信息      |
| Status         | `sstatus`                 | HS 状态           |
| Stack          | `sscratch`                | HS Trap Context |
| Interrupt      | `sie`、`sip`               | HS 中断使能与挂起状态    |
| MMU            | `satp`                    | HS Stage-1 地址空间 |
| Virtualization | `hstatus`                 | H-extension 状态  |
| Virtualization | `hedeleg`、`hideleg`       | Guest Trap 委派   |
| Virtualization | `hie`、`hip`、`hvip`        | 虚拟化中断状态         |
| Virtualization | `hgatp`                   | G-stage 地址翻译配置  |
| Virtualization | `hcounteren`、`htimedelta` | Guest 计数器相关控制   |
| Extended State | FPU、Vector 等              | 扩展执行上下文         |

这张表是用于审查的主要项目，而不是一份穷尽全部扩展的 CSR 清单。

尤其是 `hgatp`，这里要理解它属于 HS-level Virtualization Context。

Host 可能自己也运行普通 VM，所以它进入 RDSM 时：

```
hgatp
    = Host Hypervisor 原来配置的 G-stage
```

RDSM 必须防止这个值影响后续 TSM 的可信执行。

### 3.3 为什么必须保存 `satp`？

假设当前：

```
Host Linux:

satp.MODE = Sv48
satp.PPN  = HOST_ROOT_PPN
```

Host Linux 的虚拟地址：

```
VA 0xffffffe000100000
```

映射到：

```
PA 0x80201000
```

但 TSM 有自己的虚拟地址空间：

```
TSM:

satp.MODE = Sv39
satp.PPN  = TSM_ROOT_PPN
```

因此：

```
Host satp != TSM satp
```

RDSM 进入 TSM 前必须恢复 TSM 所需的地址翻译环境。

还必须处理页表变更引起的 TLB 一致性问题，不能把 `csrw satp` 简单等同于一次完整的地址空间同步。

### 3.4 建立 per-Hart Security Context

可以设计一个概念性的数据结构：

```
struct supervisor_context {
    uint64_t pc;

    uint64_t gpr[32];

    uint64_t sstatus;
    uint64_t stvec;
    uint64_t sscratch;
    uint64_t sepc;
    uint64_t sie;
    uint64_t satp;

    uint64_t hstatus;
    uint64_t hedeleg;
    uint64_t hideleg;
    uint64_t hgatp;

    /* Other hypervisor and extension state */
};

struct hart_security_context {
    struct supervisor_context host;
    struct supervisor_context tsm;

    uint64_t active_domain;
    uint64_t host_mmpt;
    uint64_t tsm_mmpt;
};
```

这是用于说明架构的数据结构，不对应某个 OpenSBI 或 TSM 仓库的实际 struct。

它的设计体现两个重要思想。

第一：

```
每个 Hart 都有当前运行状态
```

即使有 16 个 Hart，它们也可能分别运行不同的 Domain。

第二：

```
Host Context
    与
TSM Context
```

必须拥有不同的受保护保存位置。

对于 per-Hart M-mode 状态的管理，可以借鉴你熟悉的 OpenSBI `sbi_scratch` 思路，但不能认为 `sbi_scratch` 本身就自动具备 CoVE 安全上下文管理能力。

## 4. 第三阶段：RDSM 切换 Supervisor Domain

这是整个教程最核心的部分之一。

到目前为止：

```
CPU Privilege = M
```

但 CPU 还没有进入 TSM。

RDSM 现在需要完成：

```
HOST Domain
    ↓
CONFIDENTIAL Domain
```

我们以 SmMTT 当前草案为基础。

### 4.1 `mmpt` 到底是什么？

在当前 SDAP/SmMTT 草案中，`mmpt` 是 M-mode CSR：

```
CSR mmpt = 0x382
```

RV64 下的主要字段：

RV64 mmpt CSR 布局

字段位置依据当前 SmMTT 草案。相关扩展仍可能演进。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

字段含义：

- `MODE`：MPT 使用的保护模式，例如 `Smmpt43`、`Smmpt52`。
- `SDID`：当前 Hart 所在的 Supervisor Domain 标识。
- `PPN`：当前 Domain 对应的 MPT Root Physical Page Number。

注意：`SDID` 是 Hart-local 标识，不应该未经转换就直接用作 SoC 全局设备事务的安全标识。

### 4.2 为什么不仅切换 SDID，还要切换 PPN？

假设：

```
Host Domain:

SDID = 1
MPT Root = 0x88000000
```

而：

```
Confidential Domain:

SDID = 2
MPT Root = 0x89000000
```

两套 MPT 的内容不同。

同一物理页在两个 Domain 下的权限

| Memory Region     | Host MPT | TSM MPT |
| ----------------- | -------- | ------- |
| Host Kernel RAM   | R/W      | Deny    |
| TSM Private RAM   | Deny     | R/W     |
| TVM A Private RAM | Deny     | R/W     |
| Shared Buffer     | R/W      | R/W     |

示例权限，不是规范规定的固定内存布局。TSM 对 TVM 私有 RAM 的访问能力属于可信管理模型的一部分。

因此，RDSM 不能只说：

```
active_domain = CONFIDENTIAL
```

它还需要确保 CPU 后续使用 Confidential Domain 对应的保护配置。

### 4.3 RDSM 进行 Domain Switch 的伪代码

```
/*
 * Architecture-level pseudocode.
 * Not a reference implementation.
 */
void rdsm_switch_to_tsm(struct hart_security_context *hc)
{
    /* 1. Validate the caller and request */
    validate_host_request(hc);

    /* 2. Save the complete host context */
    save_host_context(&hc->host);

    /* 3. Select the confidential domain */
    activate_confidential_mpt(hc->tsm_mmpt);

    /*
     * 4. Apply required synchronization.
     * This depends on MPT changes, SDID reuse
     * and the platform's multi-hart protocol.
     */
    synchronize_domain_protection_if_needed();

    /* 5. Restore the TSM's HS-level state */
    restore_tsm_context(&hc->tsm);

    /* 6. Return from M-mode to TSM HS-mode */
    return_to_tsm();
}
```

这段逻辑强调：

Domain Switch 是一个安全状态转换过程，而不是一次普通的 CSR 写操作。

这里还必须检查一个工程细节：

当 `mmpt` 已经切换到 Confidential Domain 后，RDSM 仍在 M-mode 执行。按当前 SmMTT 草案，MPT 的普通访问检查主要针对有效特权低于 M-mode 的访问，因此 RDSM 能继续完成可信上下文切换。

不过，如果 M-mode 使用 `MPRV`、其他安全扩展或特殊内存访问方式，就必须重新验证相关权限语义。

### 4.4 `MFENCE.PA` 在什么位置使用？

这里需要纠正一个容易形成的误解：

并不是每次修改 `mmpt` 都无条件执行一次 `MFENCE.PA`。

`MFENCE.PA` 的核心用途是同步 MPT 修改与后续访问。

例如：

```
Original:

Host can read PA X
```

RDSM 修改 MPT：

```
New:

Host cannot read PA X
TSM can read PA X
```

此时必须保证旧的缓存权限状态不会继续授权访问。

在当前草案中：

```
mfence.pa x0, x0
```

表示对本 Hart 的所有 Supervisor Domain MPT 相关状态进行全范围同步。

实际使用时还可以按 Physical Address 和 SDID 缩小作用范围。

同时需要注意：

`MFENCE.PA` 本身不是跨 Hart 的完整同步协议。

对于多 Hart，必须确保其他可能持有旧权限状态的 Hart 也完成必要的同步；在权限撤销前后，还必须协调 DMA、在途事务和页面数据清理。

SmMTT 对 `mmpt` 写入、`MFENCE.PA`、`MINVAL.PA` 的具体语义已有公开草案定义。

### 4.5 `MFENCE.PA`、`SFENCE.VMA`、`HFENCE.GVMA` 有什么区别？

这是非常值得记忆的一张表。

| 指令            | 主要同步对象                         |
| ------------- | ------------------------------ |
| `SFENCE.VMA`  | S-stage 地址翻译                   |
| `HFENCE.VVMA` | VS-stage 地址翻译                  |
| `HFENCE.GVMA` | G-stage 以及相关两阶段地址翻译缓存          |
| `MFENCE.PA`   | Supervisor Domain 的 MPT 权限查询状态 |

你可以把它们对应到三类表：

```
Page Tables
    ↓
SFENCE / HFENCE

Memory Protection Tables
    ↓
MFENCE.PA
```

而且：

```
HFENCE.GVMA
    不能代替 MFENCE.PA

MFENCE.PA
    不能代替 HFENCE.GVMA
```

因为 G-stage Translation 与物理内存 Domain Permission 是独立的机制。

## 5. 第四阶段：RDSM 使用 `mret` 进入 TSM

现在 RDSM 已经完成了：

```
Host Context saved
Confidential Domain selected
TSM Context restored
```

下一步需要让 CPU 从 M-mode 返回 HS-mode。

这就是 `mret`。

### 5.1 关键汇编

以下代码只描述返回控制状态的配置步骤，前面必须已经完成可信上下文保存、恢复和权限同步。

```
# t0 = TSM entry / resume PC

csrw mepc, t0

csrr t1, mstatus

# Set MPP = S
li   t2, MSTATUS_MPP_MASK
not  t2, t2
and  t1, t1, t2

li   t2, MSTATUS_MPP_S
or   t1, t1, t2

# Ensure return virtualization mode is V=0.
# MPV handling omitted here: must be cleared.

csrw mstatus, t1

mret
```

重点理解：

```
mepc = TSM Resume PC

mstatus.MPP = S

mstatus.MPV = 0
```

执行 `mret` 之后：

```
Privilege = HS-mode
V = 0
PC = TSM Resume PC
```

同时 CPU 处于已经激活的 Confidential Domain。

这里你应该注意：

`mret` 不知道什么是 TSM、CoVE 或 Confidential VM。

它只是依据：

```
mepc
mstatus.MPP
mstatus.MPV
```

执行标准 RISC-V Trap Return。

真正的安全属性来自 RDSM 预先配置的 Domain 状态和硬件保护机制。

这和你之前研究 OpenSBI M-mode → S-mode 跳转的原理完全相同。

区别只是 CoVE 中 M-mode Firmware 还必须维护 Supervisor Domain 的隔离。

### 5.2 此时 Hart 的完整状态

```
Hart 0:

Privilege = HS
Virtualization = V0
Domain = Confidential

satp  = TSM Page Table
hgatp = Trusted virtualization context
stvec = TSM Trap Vector

PC    = TSM Resume PC
SP    = TSM Stack
```

到这里，我们只完成了：

```
Host → RDSM → TSM
```

还没有进入 TVM。

接下来的第二层切换才与 H-extension 的虚拟化机制直接相关。

## 6. 第五阶段：TSM 恢复 TVM 的执行上下文

现在 CPU 在 TSM 的 HS-mode 中。

这一步与 Host → TSM 的切换有本质区别：

```
Host → TSM:
    Supervisor Domain Switch

TSM → TVM:
    Virtualization Context Switch
```

第一步的控制者是 M-mode RDSM。

第二步的控制者是 HS-mode TSM。

### 6.1 TSM 为什么类似一个小型 Hypervisor？

因为它必须管理：

```
TVM G-stage
TVM vCPU Context
TVM Interrupt State
TVM Trap
TVM Lifecycle
```

这些都属于 Hypervisor 的核心能力。

但它与传统 Linux/KVM 不同：

TSM 不应该承担大量普通资源调度、设备驱动和通用服务职责。

它的设计目标是成为一个安全关键功能尽可能小的可信 Hypervisor。

### 6.2 TVM 的 vCPU Context 包含什么？

假设我们有：

```
TVM A
    vCPU 0
    vCPU 1

TVM B
    vCPU 0
    vCPU 1
```

每个 vCPU 都需要独立保存自己的执行状态。

示意结构：

```
struct tvm_vcpu_context {
    uint64_t gpr[32];
    uint64_t guest_pc;

    uint64_t vsstatus;
    uint64_t vsie;
    uint64_t vstvec;
    uint64_t vsscratch;
    uint64_t vsepc;
    uint64_t vscause;
    uint64_t vstval;
    uint64_t vsatp;

    uint64_t hstatus;
    uint64_t hgatp;

    /* Additional architectural state */
};
```

这里区分两类状态：

Guest 的 VS-level 状态：

```
vsstatus
vsatp
vstvec
vsepc
...
```

这些属于 Guest Linux 的虚拟 Supervisor 环境。

TSM 控制的虚拟化状态：

```
hgatp
hstatus
hedeleg
hideleg
virtual interrupt configuration
...
```

这些决定 Guest 如何被执行和管理，必须由可信 TSM 控制。

注意，某些硬件 CSR 在当前 Hart 上只有一套物理实例，因此 `hgatp` 等字段的值必须按照被调度的 TVM 切换。示例结构里的重复字段是逻辑归属，不表示硬件存在两份 CSR。

## 7. 第六阶段：配置 G-stage Page Table

这是 CoVE 真正执行 TVM 的关键环节。

我们使用一个具体例子。

假设：

```
TVM A:

Guest Physical Memory:
    GPA = 0x4000_0000

实际物理内存：
    HPA = 0x9000_0000
```

TSM 已经为 TVM A 建立好 G-stage Page Table。

### 7.1 `hgatp` 的作用

RISC-V H-extension 定义：

```
hgatp
    ├── MODE
    ├── VMID
    └── PPN
```

其中：

- `MODE`：G-stage Translation 模式。
- `VMID`：用于区分 Guest 地址翻译上下文。
- `PPN`：G-stage Root Page Table。

例如：

```
hgatp.MODE = Sv39x4
hgatp.VMID = 5
hgatp.PPN  = TVM_A_GSTAGE_ROOT_PPN
```

这里的 `VMID=5` 是虚拟化地址翻译标识，不是 Supervisor Domain 的 `SDID`。

这是两个完全不同的标识空间。

```
SDID:
    Supervisor Domain Isolation

VMID:
    Virtual Machine Translation Context
```

### 7.2 为什么使用 Sv39x4，而不是 Sv39？

普通 Linux 的 `satp` 可以使用：

```
Sv39
```

而 G-stage 可以使用：

```
Sv39x4
```

两者名字相似，但地址空间和 Root Page Table 的结构不同。

Sv39：

```
VA = 39 bits
Root Page Table = 4 KiB
```

Sv39x4：

```
GPA = 41 bits
Root Page Table = 16 KiB
```

原因是 G-stage 要支持比普通 Sv39 VA 更宽的 Guest Physical Address。

其 Root Page Table 因此扩大四倍，并要求 16 KiB 对齐。

这是 H-extension 架构中明确规定的行为。

[image](https://www.google.com/s2/favicons?domain=https://docs.riscv.org\&sz=32)

docs.riscv.org



### 7.3 G-stage Page Table 实际管理什么？

我们设定：

```
TVM A GPA 0x40001000
        ↓
HPA 0x90001000
```

TSM 创建映射：

```
G-stage PTE

GPA 0x40001000
    → HPA 0x90001000

R = 1
W = 1
X = 0
```

相应的概念代码：

```
/*
 * Illustrative TSM memory mapping operation.
 */
int tsm_map_guest_page(struct tvm *tvm,
                       uint64_t gpa,
                       uint64_t hpa,
                       uint64_t flags)
{
    if (!page_owned_by_tvm(tvm, hpa))
        return -1;

    if (!mapping_is_permitted(tvm, gpa, hpa, flags))
        return -1;

    update_gstage_pte(tvm, gpa, hpa, flags);

    synchronize_gstage_if_required(tvm);

    return 0;
}
```

其中：

```
page_owned_by_tvm()
```

不是一个真实的 CoVE API，而是用来表达安全检查逻辑。

TSM 必须确保：

1. 物理页属于允许使用的 Confidential Memory。
2. 不能非法映射其他 TVM 的私有页。
3. Shared/Private Memory 的属性与预期一致。
4. G-stage 不会引入不允许的别名或权限。
5. 页表自身不能被不可信 Host 修改。

### 7.4 为什么 Host 不能自己修改 G-stage？

这个问题非常重要。

假设：

```
TVM A:
    GPA 0x40001000 → HPA 0x90001000

TVM B:
    GPA 0x40001000 → HPA 0xA0001000
```

如果 Host 能修改 TVM A 的 G-stage：

```
TVM A:
    GPA 0x40001000 → HPA 0xA0001000
```

那么 TVM A 就可能访问到 TVM B 的私有数据。

因此，即使 MPT 已经阻止 Host 直接访问 Confidential RAM，TVM 之间的隔离仍然需要由 TSM 负责。

请注意：

MPT 只能根据当前 Domain 的权限限制物理内存访问；它并不知道当前访问者究竟是 TVM A 还是 TVM B。

在这里我们采用的模型是：

```
Domain Confidential
    ├── TSM
    ├── TVM A
    └── TVM B
```

三个组件处于同一个 Supervisor Domain 中。

真正区分 TVM A 和 TVM B 的是它们的：

```
G-stage mappings
VMID
Trusted vCPU context
```

所以：

> MPT 为 TSM 创造安全的运行环境，TSM 再利用虚拟化机制为各个 TVM 创造安全的运行环境。

## 8. 第七阶段：TSM 使用 `sret` 进入 TVM

现在我们来到整条执行链最关键的一条指令：

```
sret
```

### 8.1 为什么不是 `mret`？

因为现在：

```
CPU Privilege = HS
```

HS-mode 是 H-extension 下的 Supervisor Mode，不能直接使用 `mret` 完成自己的正常 Trap Return。

正确的虚拟化入口依赖：

```
hstatus.SPV
sstatus.SPP
sepc
sret
```

### 8.2 几个关键寄存器

| Register      | 意义                                      |
| ------------- | --------------------------------------- |
| `hstatus.SPV` | Supervisor Previous Virtualization Mode |
| `sstatus.SPP` | Supervisor Previous Privilege           |
| `sepc`        | `sret` 使用的返回 PC                         |
| `hgatp`       | Guest G-stage                           |
| `vsatp`       | Guest VS-stage                          |

当 TSM 希望进入 VS-mode：

```
hstatus.SPV = 1
sstatus.SPP = 1
sepc = Guest Resume PC
```

然后：

```
sret
```

执行之后：

```
V = 1
Privilege = VS
PC = Guest Resume PC
```

RISC-V H-extension 规定，当 `sret` 在 HS-mode 执行时，`hstatus.SPV` 会影响返回后的 Virtualization Mode。

[image](https://www.google.com/s2/favicons?domain=https://riscv-specs.timhutt.co.uk\&sz=32)

riscv-specs.timhutt.co.uk



注意 `hstatus.SPVP` 与 `SPV` 不一样：

- `SPV` 决定相应 `sret` 的 Virtualization Mode。
- `SPVP` 主要用于保存之前的 Virtual Privilege 信息，并影响 `HLV/HSV` 等特殊访存指令的权限语义。

不能用 `SPVP` 代替 `SPV`。

### 8.3 一个接近实际的汇编示例

下面只展示进入 Guest 的最后几步。它假定 Guest GPR、浮点/向量状态、虚拟化中断状态等已经正确处理。

```
# TSM running in HS-mode
# Prepared values are stored in trusted context.

# 1. Install TVM G-stage root
ld     t0, HGATP_OFFSET(s0)
csrw   hgatp, t0

# 2. Synchronize G-stage if required
hfence.gvma x0, x0

# 3. Prepare Guest resume PC
ld     t0, GUEST_PC_OFFSET(s0)
csrw   sepc, t0

# 4. Prepare return privilege: VS-mode
csrr   t0, sstatus
li     t1, SSTATUS_SPP
or     t0, t0, t1
csrw   sstatus, t0

# 5. Set hstatus.SPV
csrr   t0, hstatus
li     t1, HSTATUS_SPV
or     t0, t0, t1
csrw   hstatus, t0

# 6. Restore Guest registers (not shown)

# 7. Enter TVM
sret
```

这里有几个细节值得特别强调。

第一，`HFENCE.GVMA` 是否需要、使用什么地址和 VMID 范围，取决于此前 G-stage 是否发生修改以及相关缓存同步状态。示例中的全范围 Fence 是为了便于理解。

第二，`sret` 所需的 `sepc` 不能简单认为永远等于 Guest 的 `vsepc`。

- `sepc` 是 HS-mode 返回 Guest 时使用的 PC。
- `vsepc` 是 Guest VS-mode 自己处理异常时使用的 PC。

第三，进入 Guest 之前，TSM 必须避免将自身敏感的 GPR、FPU、Vector State 等泄露给 Guest。上面的代码没有展示完整状态恢复，因此不能直接用于生产代码。

## 9. 第八阶段：TVM 的一次真实内存访问

现在：

```
Hart 0:

Privilege = VS
Virtualization = 1
Domain = Confidential
```

TVM Linux 开始运行。

假设 Guest Kernel 执行：

```
uint64_t x = *(volatile uint64_t *)ptr;
```

其中：

```
Guest VA:
    0xffffffc000001000
```

### 9.1 第一层：VS-stage Translation

Guest Linux 管理：

```
vsatp
```

假设得到：

```
GVA 0xffffffc000001000
             │
             ▼
GPA 0x40001000
```

这是 Guest Linux 自己维护的地址翻译。

### 9.2 第二层：G-stage Translation

TSM 管理：

```
hgatp
```

继续翻译：

```
GPA 0x40001000
        │
        ▼
HPA 0x90001000
```

### 9.3 第三层：MPT Access Check

MPT 根据：

```
Current Domain = Confidential
```

检查：

```
HPA 0x90001000
```

是否允许读取。

一条 TVM Load 的完整地址路径

Guest Virtual Address

### 0xffffffc000001000

VS-stage · vsatp

Guest Physical Address

### 0x40001000

G-stage · hgatp

Host/Supervisor Physical Address

### 0x90001000

MPT · Current SDID

Access Allowed

Confidential Domain · Read permitted

数值只是示例。物理保护和翻译缓存检查可在硬件中流水化执行，不要求严格按图中的软件顺序逐步执行。

在这个例子中，三个检查必须同时成立。

```
VS-stage:
    Guest VA 映射合法

G-stage:
    Guest GPA 映射合法

MPT:
    Confidential Domain 具有访问权限
```

任何一个安全检查失败，都不能完成这次受保护的读取。

### 9.4 如果 Host 试图访问同一个 HPA 呢？

现在切回 Host：

```
Privilege = HS
Domain = Host
```

Host 尝试通过自己的 `satp` 把：

```
Host VA → HPA 0x90001000
```

即使 Stage-1 Page Table 允许这次访问，MPT 仍然会检查：

```
Current Domain = HOST

Target PA = 0x90001000

MPT Permission = Deny
```

因此：

```
Load denied
```

根据当前 Smmpt 草案，此类 MPT 访问违反会触发与原始访存类型对应的 Access Fault，而相关 Domain 安全管理需要交由 M-mode RDSM 处理。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub+1



这里的核心设计是：

Hypervisor 的页表权限不能覆盖更底层的 Supervisor Domain 物理保护权限。

这也正是 CoVE 能抵抗恶意 Host 的硬件基础之一。

## 10. 第九阶段：TVM 发生 Trap，如何回到 TSM？

到这里我们已经完成了一次 TVM Entry。

接下来分析反向路径：

```
TVM → TSM → RDSM → Host
```

这里涉及三个完全不同的 Trap 情景。

### 10.1 情景 A：Guest Linux 自己处理异常

假设 TVM 内的用户程序发生一次普通 Page Fault。

```
TVM User Application
       │
       │ Page Fault
       ▼
Guest Linux
```

如果异常已经正确委派给 VS-mode：

```
VU-mode
    ↓
VS-mode
```

此时：

```
vscause = Guest Page Fault Cause
vsepc   = Guest Fault PC
vstval  = Fault Address
PC      = vstvec
```

TSM 不需要参与。

这与普通 RISC-V Linux 的用户态异常处理基本一致。

机密计算不能让 Guest 中所有 Trap 都进入 TSM，否则性能会非常糟糕。

### 10.2 情景 B：Guest 发生需要 TSM 处理的 VM Exit

例如：

- Guest 执行未委派给 VS-mode 的 `ecall`。
- G-stage Page Fault。
- 需要由 TSM 处理的虚拟化异常。
- 某些需要安全管理的 Interrupt 或 I/O 事件。

假设这次异常从 VS-mode 进入 HS-mode TSM。

硬件会保存：

```
sepc
scause
stval

htval
htinst
hstatus
```

对于来自 VS-mode 的 Trap：

```
hstatus.SPV = 1
sstatus.SPP = 1
```

因为异常发生前：

```
V = 1
Privilege = VS
```

异常发生后：

```
V = 0
Privilege = HS
PC = TSM stvec
```

这几个状态非常值得记忆。

尤其是：

```
Guest → TSM
```

和：

```
Host → RDSM
```

是两条不同的 Trap 路由。

前者主要受 H-extension Trap Delegation 机制控制。

后者需要通过 M-mode Trap Routing 与 RDSM 实现。

### 10.3 TSM 如何处理 G-stage Page Fault？

假设：

```
GPA = 0x40003000
```

但当前 G-stage 中不存在合法映射。

CPU 可能产生：

```
Instruction Guest-Page Fault
Load Guest-Page Fault
Store/AMO Guest-Page Fault
```

对应 Exception Code：

| Exception                    | Code |
| ---------------------------- | ---- |
| Instruction Guest-Page Fault | 20   |
| Load Guest-Page Fault        | 21   |
| Store/AMO Guest-Page Fault   | 23   |

TSM 可以检查：

```
csrr t0, scause
csrr t1, sepc
csrr t2, stval
csrr t3, htval
csrr t4, htinst
```

需要注意：

`htval` 不是无条件保存完整 GPA。

对于 Guest-Page Fault 等情景，它可以提供经过右移编码的 Guest Physical Address 信息，具体必须按照 H-extension 的 Trap 语义恢复和解释。

因此不能直接写：

```
gpa = htval;
```

而应依据异常类型、`htval` 定义以及必要时的 `stval` 信息分析。

对于对应场景，Guest Physical Address 的相关部分以 `htval << 2` 的方式解释，低位处理依赖具体异常。

[image](https://www.google.com/s2/favicons?domain=https://riscv-specs.timhutt.co.uk\&sz=32)

riscv-specs.timhutt.co.uk



TSM 随后判断：

```
Is this a valid memory access?

Is the page missing because of demand allocation?

Is this an MMIO emulation request?

Is the target GPA part of shared memory?

Is this a security violation?
```

如果能够安全解决，就更新相应状态，必要时进行 G-stage Translation 同步，然后恢复 TVM。

如果需要 Host 提供设备仿真或资源，则可能产生一个受控的 TVM Exit。

## 11. 第十阶段：TSM 如何安全地把执行权还给 Host？

现在假设：

```
TVM
    │
    │ MMIO access
    ▼
TSM
```

TSM 需要 Host 做设备仿真。

但绝不能简单地：

```
memcpy(host_buffer, tvm_vcpu_context,
       sizeof(tvm_vcpu_context));
```

因为这可能泄露：

```
Guest GPR
Guest PC
Guest private memory state
Sensitive CSR
```

正确的思路是区分：

```
Private vCPU State
```

和：

```
Host-visible Exit State
```

CoVE 的相关设计通过受控共享状态（例如 NACL shared memory）提供 Guest Exit 所需的信息，并限制 Host 对 TVM 状态的可见性。

[image](https://www.google.com/s2/favicons?domain=https://lists.riscv.org\&sz=32)

lists.riscv.org



### 11.1 生成受控的 Exit Information

示例：

```
struct tvm_exit_info {
    uint64_t exit_reason;
    uint64_t shared_gpa;
    uint64_t mmio_size;
    uint64_t mmio_direction;
};
```

这只是逻辑示例。

TSM 可以把允许 Host 使用的信息放入预先建立的 Shared Buffer。

例如：

```
Exit Reason = MMIO
Device = virtual UART
Access Size = 4 bytes
```

Host 处理后，再通过受控接口请求恢复 TVM。

Shared Buffer 是跨安全边界的输入输出接口，必须按不可信数据处理。

哪怕它由 TSM 写入，Host 也可能在后续调用中篡改其中的字段。因此 TSM 必须重新验证输入、长度、偏移和状态转换是否合法。

### 11.2 TSM 如何返回 RDSM？

TSM 运行在 HS-mode。

需要跨域回到 Host 时：

```
TSM
    │
    │ ecall
    ▼
RDSM
```

如果该请求通过 M-mode SBI 路由，硬件再次产生：

```
mcause = 9
mepc   = TSM ECALL PC
mstatus.MPP = S
mstatus.MPV = 0
```

RDSM 现在完成相反方向的 Context Switch：

```
① Save TSM HS Context

② Validate exit request

③ Switch Supervisor Domain:
       Confidential → Host

④ Restore Host HS Context

⑤ Prepare mstatus.MPP = S
   Prepare mstatus.MPV = 0

⑥ Restore Host resume PC

⑦ mret
```

执行 `mret` 后：

```
Privilege = HS
Domain = Host
PC = Host Resume PC
```

Host Linux/KVM 的执行继续进行。

这就完成了一次：

```
Host
  ↓
RDSM
  ↓
TSM
  ↓
TVM
  ↓
TSM
  ↓
RDSM
  ↓
Host
```

的完整运行循环。

## 12. 从 CSR 角度，把整个过程重新串联起来

理解这张表之后，CoVE 的 CPU 状态切换基本就清晰了。

| 执行阶段          | Mode | Domain       | 关键状态                      |
| ------------- | ---- | ------------ | ------------------------- |
| Host KVM      | HS   | Host         | `satp=Host`               |
| Host `ecall`  | M    | 过渡中          | `mepc`、`mcause`           |
| RDSM          | M    | 可信管理         | 保存 Host Context           |
| Domain Switch | M    | Confidential | `mmpt`、MPT 同步             |
| TSM           | HS   | Confidential | `satp=TSM`                |
| TVM Entry 准备  | HS   | Confidential | `hgatp`、`vsatp`、`hstatus` |
| `sret` 后      | VS   | Confidential | Guest Linux 运行            |
| Guest VM Exit | HS   | Confidential | `scause`、`sepc`、`htval`   |
| TSM `ecall`   | M    | 过渡中          | 保存 TSM Context            |
| 返回 Host       | HS   | Host         | 恢复 Host Context           |

这里有三个很容易混淆的关键概念。

`satp` 管理的是当前 HS 软件自身的 Stage-1 地址空间。

`vsatp` 管理的是 TVM Guest Linux 的 VS-stage 地址空间。

`hgatp` 管理的是 TVM GPA 到物理地址的 G-stage 翻译。

而：

`mmpt` 管理的是当前 Supervisor Domain 的物理内存访问保护配置。

它并不完成普通意义上的地址翻译。

## 13. 如果在真实 SoC 上调试，应该如何观察这条链？

对于 ZeBu、Palladium 或支持对应扩展的 CPU 模型，我建议建立一个固定的诊断方法。

不要一上来只看某个 `panic()` 或 Exception Code，而是检查每次执行阶段是否满足预期状态。

交互式 CSR / Trap 调试检查表

1\. Host → RDSM

M-mode

Host → RDSM

mcause 是否等于预期 SBI Exception

mepc 是否指向 Host ecall

mstatus.MPP / MPV 是否符合 HS 来源

mscratch 是否指向可信的 Trap Context

### 13.1 典型 Debug Trace

对于一个自行实现的 RDSM/TSM，可以考虑输出如下日志：

```
[RDSM] hart=0, enter from HOST
[RDSM] mcause=9, mepc=0x80201000
[RDSM] save HOST context

[RDSM] switch HOST -> CONFIDENTIAL
[RDSM] load TSM MMPT
[RDSM] restore TSM context

[TSM] COVH run TVM=1, vCPU=0
[TSM] load hgatp
[TSM] restore guest VS context
[TSM] enter TVM

[TSM] guest exit
[TSM] scause=...
[TSM] save TVM context
[TSM] prepare host-visible exit

[RDSM] switch CONFIDENTIAL -> HOST
[RDSM] restore HOST context

[HOST] vCPU run returned
```

这些是建议的调试点，不是某个真实平台已经存在的日志字符串。

真正调试时，还要特别注意日志可能包含 Secret，生产固件中不应随意输出 TVM 私有寄存器和内存内容。

### 13.2 三个最容易出现 Bug 的地方

问题一：Domain 已经切换，但 `satp` 没有正确恢复。

现象：

```
RDSM successfully mret
    ↓
TSM Instruction Page Fault
```

原因可能是 TSM 虚拟地址仍按 Host 的 Page Table 翻译。

问题二：`hgatp` 已经切换，但缺少必要的 G-stage 同步。

现象可能是：

```
TVM A 被调度
    ↓
访问错误物理页
```

需要分析 VMID 复用、G-stage 页表更新及 `HFENCE.GVMA` 的作用范围。

问题三：MPT 已更新，但其他 Hart 仍持有旧的权限检查状态。

这种问题尤其危险。

假设：

```
Hart 0:
    把 Page X 从 Host 转换为 Confidential

Hart 1:
    仍然持有旧的 Host 访问权限缓存
```

那么即使 Hart 0 上的转换看起来成功，系统整体的安全不变量仍可能不成立。

这是多 Hart CoVE 实现中需要重点设计和验证的部分。

## 15. 最后，从架构设计角度总结这条执行链

我们从普通 Linux/KVM 进入 TVM，实际上经过了两次不同层次的安全上下文切换。

第一次：Host → TSM

```
HOST HS-mode
      │
      │ ecall
      ▼
M-mode RDSM
      │
      ├── Supervisor Context Switch
      ├── Domain Protection Switch
      └── Security State Isolation
      │
      │ mret
      ▼
TSM HS-mode
```

它解决的问题是：

如何让两个平级的 HS-mode 软件环境互相隔离？

第二次：TSM → TVM

```
TSM HS-mode
      │
      ├── G-stage
      ├── vCPU State
      ├── Guest Trap Routing
      │
      │ sret
      ▼
TVM VS-mode
```

它解决的问题是：

如何让一个可信 Hypervisor 安全地运行多个 Confidential VM？

这两个问题结合起来，才能理解 CoVE 的整个运行体系。

### 与 Arm CCA 最本质的对应

| 执行层次     | RISC-V CoVE             | Arm CCA          |
| -------- | ----------------------- | ---------------- |
| 不可信资源管理  | Host HS-mode            | Normal EL2       |
| 安全边界切换   | M-mode RDSM             | Root EL3 Monitor |
| 外层内存隔离   | Supervisor Domain / MPT | RME GPT/GPC      |
| 可信 VM 管理 | TSM HS-mode             | RMM R-EL2        |
| VM 执行    | TVM VS-mode             | Realm R-EL1      |
| VM 地址翻译  | G-stage                 | Realm Stage-2    |

从架构思想来看，两者几乎都在解决同一道题：

> 让不可信 Host 保留 VM 的资源管理能力，但把安全状态、内存归属、可信地址翻译和私有 CPU 上下文交给更小的可信管理层。

区别只是 Arm 采用 RME 定义的 Security State 和 Realm 执行环境，而 RISC-V 可以基于 Supervisor Domain 与现有特权/虚拟化机制组合实现。

对你接下来深入 CoVE 最有价值的研究点，我认为是 RDSM 的 per-Hart Context Switch，以及 MPT 修改与 G-stage TLB 同步之间的关系。

因为 `ecall`、`mret`、`sret` 本身并不复杂。真正决定一个 CoVE 实现能否安全运行的，是 Domain Switch 前后，所有能够影响资源访问的 CPU、内存、缓存和设备状态，是否始终满足同一套安全不变量。

这才是从理解 CoVE 规范，走向实际设计和实现 CoVE 的分界点。
