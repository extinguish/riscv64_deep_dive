# RISC-V OP-TEE 实战调试手册：QEMU + GDB + OpenSBI + OP-TEE + Linux

这次直接进入实操。以下以你正在使用的 RISE RP016 `rp016_m1` + Buildroot + WSL2 为基线，重点是建立一套能够跨越 M-mode、S-mode、OP-TEE Domain 和 Linux Kernel 的调试工作流。

我核对了该分支的 Buildroot 配置、QEMU 启动脚本模板、OpenSBI Domain Context 源码及 OP-TEE RISC-V 入口汇编，下面的关键符号和构建选项均针对这一基线。

## 1. 启动 QEMU：其实不需要修改 `start-qemu.sh`

这是第一个重要发现。

RISE 的 `start-qemu.sh` 已经支持通过 `--` 将后面的参数原样传递给 QEMU。因此直接执行：

```
cd ~/riscv_tee_dev/integrated/buildroot-rp016

./output/images/start-qemu.sh -- -S -s
```

就可以实现：

- `-S`：启动后暂停所有 Guest CPU，等待 GDB。
- `-s`：开启默认 TCP 1234 端口的 GDB Stub。

这是因为该脚本最后通过 `"$@"` 把额外参数传递给 QEMU。

[image](https://www.google.com/s2/favicons?domain=https://gitlab.com\&sz=32)

GitLab



考虑到 WSL2 网络暴露问题，我更推荐只监听回环地址：

```
./output/images/start-qemu.sh -- \
    -S \
    -gdb tcp:127.0.0.1:1234
```

这就是你以后最常用的 QEMU Debug 启动命令。

### 如果希望永久修改脚本

编辑：

```
nano output/images/start-qemu.sh
```

找到最后一行 `exec ...`，将：

```
exec <原有QEMU命令和参数> ${EXTRA_ARGS} "$@"
```

改为：

```
exec <原有QEMU命令和参数> ${EXTRA_ARGS} -S -s "$@"
```

这里的 `<原有QEMU命令和参数>` 表示保留你脚本中的原始命令，而不是输入字面上的占位符。

不过，`output/images/start-qemu.sh` 是 Buildroot 生成的文件，后续重新生成镜像时可能被覆盖。通过 `-- -S -s` 传参更简洁。

### 三个 Terminal 的安排

| Terminal   | 用途                            | 命令                                       |
| ---------- | ----------------------------- | ---------------------------------------- |
| Terminal 1 | QEMU                          | `./output/images/start-qemu.sh -- -S -s` |
| Terminal 2 | Linux / OpenSBI / U-Boot UART | `telnet 127.0.0.1 64320`                 |
| Terminal 3 | GDB                           | `gdb-multiarch`                          |

RP016 的 UART 配置确实使用 TCP `64320`，GDB 则使用独立的 `1234` 端口。

## 2. 先找对 ELF：`fw_payload.elf` 不是 Linux ELF

这一点非常重要。

你目前这套 RP016 启动链实际使用的是：

```
QEMU
  |
  v
U-Boot SPL
  |
  +-- OpenSBI fw_dynamic.bin
  |
  +-- OP-TEE tee.bin
  |
  +-- U-Boot Proper
        |
        v
      Linux Image
```

所以应当寻找以下符号文件：

| 调试目标          | 推荐 ELF           |
| ------------- | ---------------- |
| U-Boot SPL    | `u-boot-spl`     |
| OpenSBI       | `fw_dynamic.elf` |
| OP-TEE Core   | `tee.elf`        |
| U-Boot Proper | `u-boot`         |
| Linux Kernel  | `vmlinux`        |

`fw_payload.elf` 是 OpenSBI 的 Payload Firmware ELF，不等于 Linux 的 `vmlinux`。只有实际采用 `fw_payload` 启动方案时，才需要把它作为相应的 OpenSBI 固件符号文件。

你的 RP016 U-Boot FIT 明确装载的是 `fw_dynamic.bin`。

[image](https://www.google.com/s2/favicons?domain=https://gitlab.com\&sz=32)

GitLab



在 Buildroot 根目录执行：

```
find output/build -type f \
  \( -name 'fw_dynamic.elf' \
  -o -name 'tee.elf' \
  -o -name 'vmlinux' \
  -o -name 'u-boot-spl' \
  -o -name 'u-boot' \) \
  -print
```

注意 `vmlinux` 通常位于 Linux Build Directory，`Image` 是部署用的 Kernel Image，不是最适合 GDB 源码调试的符号文件。

如果 `vmlinux` 未包含完整调试信息，检查当前 Linux 配置中的 `CONFIG_DEBUG_INFO`，必要时重新构建 Debug Kernel。

## 3. 一次性加载 OpenSBI、OP-TEE、Linux 三套 ELF

### 3.1 自动定位 ELF

在 Buildroot 根目录执行：

```
export SBI_ELF="$(find output/build -type f \
    -name fw_dynamic.elf -print -quit)"

export TEE_ELF="$(find output/build -type f \
    -name tee.elf -print -quit)"

export LINUX_ELF="$(find output/build -type f \
    -name vmlinux -print -quit)"

printf 'OpenSBI: %s\n' "$SBI_ELF"
printf 'OP-TEE:  %s\n' "$TEE_ELF"
printf 'Linux:   %s\n' "$LINUX_ELF"
```

确保三个路径都非空，并且对应当前 QEMU 使用的编译基线。

将相对路径转换为绝对路径：

```
export SBI_ELF="$(realpath "$SBI_ELF")"
export TEE_ELF="$(realpath "$TEE_ELF")"
export LINUX_ELF="$(realpath "$LINUX_ELF")"
```

### 3.2 启动 GDB 并加载三个 ELF

可以直接使用：

```
gdb-multiarch -q \
    -ex 'set pagination off' \
    -ex 'set print pretty on' \
    -ex 'set architecture riscv:rv64' \
    -ex "file $SBI_ELF" \
    -ex "add-symbol-file $TEE_ELF" \
    -ex "add-symbol-file $LINUX_ELF" \
    -ex 'target extended-remote 127.0.0.1:1234'
```

这里：

- `file`：将 OpenSBI ELF 作为主要符号文件。
- `add-symbol-file`：额外加入 OP-TEE 和 Linux 的符号表。
- `extended-remote`：连接 QEMU，支持后续多 cluster 调试。

GDB 支持添加多个符号文件，但不会自动替你计算运行时的 ASLR/KASLR 偏移。

[image](https://www.google.com/s2/favicons?domain=https://sourceware.org\&sz=32)

Sourceware



进入 GDB 后，先检查：

```
info files

info address sbi_init

info address boot_init_primary_runtime

info address start_kernel

info threads
```

三个函数应当分别来自 OpenSBI、OP-TEE 和 Linux。

如果 `info address` 没有解析到预期函数，先不要继续设置断点，检查对应 ELF 的 Debug Symbols 及源码版本。

### 3.3 第一次使用时建议开启的 GDB 设置

```
set pagination off
set print pretty on
set print elements 0
set disassemble-next-line on
set breakpoint pending on

set history save on
set history filename ~/.gdb_history

set logging file /tmp/riscv-tee-gdb.log
set logging overwrite off
set logging enabled on
```

`set breakpoint pending on` 适合调试尚未加载符号的模块，但也可能掩盖符号拼写错误。因此，对下面的关键函数，最好先用 `info address` 确认它们存在。

## 4. 第一组高级断点：追踪完整 Boot Chain

这组断点最值得首先运行一次。

### 4.1 OpenSBI 入口与 Domain 初始化

```
hbreak sbi_init

hbreak sbi_domain_context_enter

hbreak switch_to_next_domain_context

hbreak sbi_domain_context_exit

hbreak sbi_hart_switch_mode
```

对应关系：

| 函数                                | 调试目标                 |
| --------------------------------- | -------------------- |
| `sbi_init()`                      | OpenSBI 的 M-mode 初始化 |
| `sbi_domain_context_enter()`      | 进入另一个 Domain         |
| `switch_to_next_domain_context()` | 保存/恢复 Domain Context |
| `sbi_domain_context_exit()`       | 离开当前 Domain          |
| `sbi_hart_switch_mode()`          | 配置目标执行状态，准备 `mret`   |

这些函数均可以在 RP016 的 OpenSBI 实现中找到。

[image](https://www.google.com/s2/favicons?domain=https://gitlab.com\&sz=32)

GitLab+2



建议先设置：

```
hbreak sbi_hart_switch_mode
continue
```

当命中断点时：

```
info registers a0 a1 a2 a3
info registers mepc mstatus
x/16i $pc
bt
```

在当前 OpenSBI 实现中，函数原型为：

```
void sbi_hart_switch_mode(
    unsigned long arg0,
    unsigned long arg1,
    unsigned long next_addr,
    unsigned long next_mode,
    bool next_virt);
```

在函数入口，按 RISC-V 调用约定：

| 寄存器  | 含义                  |
| ---- | ------------------- |
| `a0` | 下一阶段的参数 a0          |
| `a1` | 下一阶段的参数 a1          |
| `a2` | 下一阶段的 Entry Address |
| `a3` | 目标 Privilege Mode   |
| `a4` | 目标虚拟化状态             |

例如：

```
p/x $a2
p/d $a3
```

若 `a3 == 1`，表示 `PRV_S`。

这里要注意，此时刚进入 C 函数，`mepc` 和 `mstatus.MPP` 可能还没修改。你需要单步到实际写入 CSR 的指令之后再检查。

### 4.2 OP-TEE Boot 断点

这些符号来自 RP016 的实际 `entry.S` 和 `boot.c`：

```
hbreak boot_init_primary_early

hbreak boot_init_primary_late

hbreak boot_init_primary_runtime

hbreak boot_init_primary_final

hbreak boot_primary_init_sbi_mpxy
```

OP-TEE 入口 `_start` 与其他 Firmware 可能存在同名符号，建议先：

```
info files
info address boot_init_primary_early
```

如果要在真正的 OP-TEE 第一条指令处停下，可以从 `tee.elf` 查明 `_start` 的链接地址，再与 FIT 中的装载地址核对。

在你这套 RP016 配置中，OP-TEE 物理装载位置为：

```
0xF1000000
```

所以早期可以尝试：

```
hbreak *0xF1000000
```

但这个断点只有在该地址确实是当前镜像的入口指令地址时才成立。使用 `readelf -h`、`nm` 和 `dumpimage -l` 核实后，再把它作为固定调试断点。

### 4.3 Linux Kernel Boot 断点

```
hbreak start_kernel

hbreak setup_arch

hbreak rest_init
```

第一次建议只保留：

```
hbreak start_kernel
```

当命中后：

```
info registers
bt
list
x/16i $pc
p/x $satp
```

在 Linux `start_kernel()` 断下，意味着已经完成了大部分早期汇编初始化，包括进入 C Runtime 所需的基本环境。

但它并不意味着 RootFS 已挂载或用户空间已启动。

### 4.4 推荐的 Boot Debug 时间线

```
U-Boot SPL
   |
   v
OpenSBI sbi_init()
   |
   v
sbi_domain_context_exit()
   |
   v
switch_to_next_domain_context()
   |
   v
sbi_hart_switch_mode()
   |
   v
OP-TEE Entry
   |
   v
boot_init_primary_early()
   |
   v
boot_init_primary_runtime()
   |
   v
boot_init_primary_final()
   |
   v
OP-TEE Returns to Normal Domain
   |
   v
U-Boot Proper
   |
   v
Linux start_kernel()
```

这是供你追踪的主要节点，而不是保证每个节点只命中一次的严格调用序列。实际启动会涉及 Secondary Hart、Domain 初始化状态和不同的返回路径。

## 5. 第二组高级断点：深入 Domain Context Switch

这是我最建议你重点研究的一组断点。

RP016 的 `sbi_domain_context.c` 中实际保存了以下状态：

```
struct hart_context {
    struct sbi_trap_context trap_ctx;

    unsigned long sstatus;
    unsigned long sie;
    unsigned long stvec;
    unsigned long sscratch;
    unsigned long sepc;
    unsigned long scause;
    unsigned long stval;
    unsigned long sip;
    unsigned long satp;
    unsigned long scounteren;
    unsigned long senvcfg;

    struct sbi_domain *dom;
    struct hart_context *prev_ctx;
    bool initialized;
};
```

这正是需要结合 GDB 观察的结构。

[image](https://www.google.com/s2/favicons?domain=https://gitlab.com\&sz=32)

GitLab



### 5.1 在 Context Switch 函数中断下

```
hbreak switch_to_next_domain_context
continue
```

命中后查看：

```
info args
info locals

p *ctx
p *dom_ctx

p ctx->dom->name
p dom_ctx->dom->name

p/x ctx->satp
p/x dom_ctx->satp
```

`ctx` 是当前 Domain 的上下文，`dom_ctx` 是目标 Domain 的上下文。

如果这些局部变量无法被 GDB 识别，优先检查 OpenSBI 是否带有 DWARF 信息以及相关函数是否被优化。

### 5.2 查看 Domain 切换前的关键 CSR

```
info registers \
    mstatus mepc mscratch \
    sstatus stvec sepc sscratch satp \
    scause stval sie sip
```

如果某些 CSR 不受当前 QEMU/GDB 版本支持，可以逐项查询：

```
p/x $satp
p/x $sstatus
p/x $stvec
p/x $sscratch
```

然后单步到 `csr_swap()` 对应的指令位置：

```
disassemble /r switch_to_next_domain_context
```

在实际 CSR Swap 指令前后，分别执行：

```
p/x $satp
si
p/x $satp
```

同样可以观察 `sstatus`、`stvec` 等状态。

### 5.3 查看 PMP 配置变化

RP016 Milestone 1 的 `switch_to_next_domain_context()` 会重新配置 PMP，之后执行 CSR Context Swap。

你可以检查：

```
info registers pmpcfg0
info registers pmpaddr0
info registers pmpaddr1
info registers pmpaddr2
info registers pmpaddr3
```

然后深入对应源码：

```
hbreak sbi_hart_pmp_configure
```

记录 Domain 切换前后的 PMP 状态。

这一步尤其重要：`satp` 发生变化不代表物理内存安全域已经完成隔离。 两者是不同层面的机制。

## 6. 第三组断点：从 Linux 追踪一次 OP-TEE Call

这部分最适合在系统成功启动后运行 `xtest`。

我建议分三层设置断点。

### 6.1 Linux TEE Driver

先从 Linux GDB Symbol 中查找驱动函数：

```
info functions optee
info functions tee_ioctl
```

然后找到实际使用的 Transport 函数。

在 WSL2 Host 中也可以搜索：

```
grep -RnsE 'rpmi|mpxy|sbi' \
    output/build/linux-*/drivers/tee/ \
    | head -80
```

RP016 的 Linux TEE Driver 包含 RISC-V SBI 支持，但不同版本的传输函数位置可能变化。因此这一层最好根据本地源码确认后设置断点，不直接套用 Arm 平台的 `optee_smc_*` 路径。

Linux TEE Framework 层可以从这些函数开始：

```
info functions tee_ioctl
info functions optee_invoke
```

### 6.2 OpenSBI 的 SBI ECALL 入口

在 OpenSBI 中：

```
hbreak sbi_ecall_handler
```

如果希望只捕获来自 S-mode 的 ECALL，可以在 Trap Handler 断下后检查：

```
p/x $mcause
p/x $mepc
p/x $a7
p/x $a6
```

通常：

| 寄存器          | 作用               |
| ------------ | ---------------- |
| `mcause = 9` | S-mode ECALL     |
| `mepc`       | 发起 ECALL 的指令地址   |
| `a7`         | SBI Extension ID |
| `a6`         | SBI Function ID  |
| `a0–a5`      | SBI 参数           |

在 OpenSBI 对应入口可以检查实际参数，但应记住陷阱处理代码可能会先保存并修改 GPR。越靠近 Trap Entry，越容易观察原始调用状态。

需要筛选 ECALL 时：

```
hbreak sbi_trap_handler if $mcause == 9
```

这是基于 GDB 支持读取 `mcause` 的条件断点。若目标没有暴露该 CSR，就在 Trap Handler 中使用寄存器保存结构进行判断。

### 6.3 OP-TEE 的 MPXY/RPMI 请求路径

我核对了 RP016 的 `sbi_mpxy.c`。有一个值得注意的实现细节：

RP016 使用 MPXY ReqFwd 取回当前请求，OP-TEE 内部的 `thread_return_to_udomain_by_sbi_mpxy()` 实现包含一个持续处理请求的消息循环。

因此，不应该把它机械地理解为每次都会立即跳转回 Linux 的简单返回函数。

[image](https://www.google.com/s2/favicons?domain=https://gitlab.com\&sz=32)

GitLab



推荐断点：

```
hbreak boot_primary_init_sbi_mpxy

hbreak thread_sbi_mpxy_reqfwd_retrieve_message

hbreak thread_handle_request

hbreak thread_handle_std_abi

hbreak thread_handle_fast_abi

hbreak thread_return_to_udomain_by_sbi_mpxy
```

实际执行链中的关键节点是：

```
Linux TEE Call
       |
       v
OpenSBI SBI / MPXY
       |
       v
OP-TEE ReqFwd Channel
       |
       v
thread_sbi_mpxy_reqfwd_retrieve_message()
       |
       v
thread_handle_request()
       |
       +-- Standard ABI
       |      thread_handle_std_abi()
       |
       +-- Fast ABI
              thread_handle_fast_abi()
       |
       v
Complete Current Message
```

在 `thread_handle_request()` 中可以直接查看：

```
p *args

p/x args->a0
p/x args->a1
p/x args->a2
p/x args->a3
```

其中 `args->a0` 携带 ABI Function ID，可用于区分 Fast Call 和 Standard Call。

第一次建议先使用一个简单的 xtest Case，而不是直接运行大量测试。这样更容易识别单次调用与对应的 RPC。

## 7. Trap / Exception 调试的实用命令

### 7.1 OP-TEE Trap Entry

在 RISC-V OP-TEE 中，入口汇编提供了：

```
thread_trap_vect:
    csrrw tp, CSR_XSCRATCH, tp
    bnez  tp, 0f

    csrrw tp, CSR_XSCRATCH, tp
    j trap_from_kernel

0:
    j trap_from_user
```

这是 RP016 `thread_rv.S` 中的实际入口逻辑。

[image](https://www.google.com/s2/favicons?domain=https://gitlab.com\&sz=32)

GitLab



可以设置：

```
hbreak thread_trap_vect
```

命中后：

```
info registers

p/x $scause
p/x $sepc
p/x $stval
p/x $sstatus
p/x $sscratch

x/12i $pc
```

注意：这是一个非常高频的断点，系统正常运行后建议关闭，或者添加条件。

### 7.2 常见异常快速判断

| `scause` Exception Code | 典型含义                   |
| ----------------------- | ---------------------- |
| 2                       | Illegal Instruction    |
| 5                       | Load Access Fault      |
| 7                       | Store/AMO Access Fault |
| 8                       | ECALL from U-mode      |
| 12                      | Instruction Page Fault |
| 13                      | Load Page Fault        |
| 15                      | Store/AMO Page Fault   |

RV64 的 `scause` 最高位表示 Interrupt/Exception 区分，剩余字段包含 Cause Code。

例如：

```
p/x $scause
p/d ($scause & 0x7fffffffffffffff)
```

如果是 Page Fault：

```
p/x $sepc
p/x $stval
p/x $satp

x/12i $sepc
```

其中：

- `sepc`：发生异常的指令地址。
- `stval`：对于相关 Page Fault，通常是触发 Fault 的 VA。
- `satp`：当前 S-mode 地址转换配置。

遇到 `Instruction Page Fault`，应优先检查 `sepc` 对应的取指 VA；遇到 Data Page Fault，检查出错指令与 `stval`。

### 7.3 在触发异常前使用 Watchpoint

比如你已经定位某个内存变量可能被意外覆盖：

```
watch *(unsigned long long *)0xXXXXXXXX
```

这里将 `0xXXXXXXXX` 替换为当前能够被正确访问的运行时地址。

也可以使用：

```
rwatch *(unsigned long long *)0xXXXXXXXX
awatch *(unsigned long long *)0xXXXXXXXX
```

分别监控读访问，以及读写访问。

QEMU TCG System Emulation 支持硬件断点及 Watchpoint 的模拟，通常比仅靠日志更适合定位内存破坏问题。

## 8. 五个我最推荐的高级 GDB 技巧

### 技巧一：使用 QEMU GDB Stub 直接查看物理内存

这是研究 PMP、MMU、页表和 Firmware Image Layout 时非常有用的能力。

QEMU GDB Stub 支持切换物理地址访问模式。

首先检查：

```
maintenance packet qqemu.PhyMemMode
```

切换为 Physical Memory Mode：

```
maintenance packet Qqemu.PhyMemMode:1
```

然后直接读取 OP-TEE 的物理内存：

```
x/32gx 0xF1000000
```

检查完后恢复：

```
maintenance packet Qqemu.PhyMemMode:0
```

这个能力可以避免被当前 `satp` 的 Virtual Address Translation 干扰。

[image](https://www.google.com/s2/favicons?domain=https://www.qemu.org\&sz=32)

QEMU documentation



但这里要强调：GDB Stub 对 Guest 物理内存的直接检查是调试能力，不代表 Linux S-mode 自身能够绕过 PMP 访问同一物理地址。

### 技巧二：解析 `satp`

在 RV64 中：

```
p/x $satp
```

查看 MMU Mode：

```
p/x (($satp >> 60) & 0xf)
```

常见值：

| Mode | 地址转换 |
| ---- | ---- |
| 0    | Bare |
| 8    | Sv39 |
| 9    | Sv48 |
| 10   | Sv57 |

查看 ASID：

```
p/x (($satp >> 44) & 0xffff)
```

计算根页表物理地址：

```
set $ptroot = ($satp & 0xfffffffffff) << 12

p/x $ptroot
```

切换为物理内存模式：

```
maintenance packet Qqemu.PhyMemMode:1

x/16gx $ptroot

maintenance packet Qqemu.PhyMemMode:0
```

这样就可以开始手动分析 Sv39/Sv48 Page Table Walk。

对于你后面准备深入的 `core/mm/` 和 RISC-V MMU 实现，这个技巧尤其有价值。

### 技巧三：调试多 Hart

RP016 当前配置采用两个 hart：

```
-smp 2
```

进入 GDB：

```
info threads
```

在单一 QEMU CPU Cluster 中，通常可以看到类似：

```
1.1    Hart 0
1.2    Hart 1
```

切换到另一个 Hart：

```
thread 1.2
```

然后：

```
info registers
bt
x/10i $pc
```

一次查看所有 Hart 的状态：

```
thread apply all info registers
```

或者：

```
thread apply all bt
```

这里的 GDB Thread 通常表示 QEMU vCPU，而不是 Linux Task 或 OP-TEE Trusted Thread。

如果你的 QEMU 平台包含多个 CPU Cluster，则需要通过 `extended-remote` 连接不同 Inferior；也可以开启：

```
set schedule-multiple on
```

以便继续执行时恢复所有已连接的 Cluster。

### 技巧四：调整单步时的中断行为

QEMU 默认单步通常会屏蔽 IRQ/Timer 对单步的打扰。

检查：

```
maintenance packet qqemu.sstepbits
```

以及：

```
maintenance packet qqemu.sstep
```

通常会看到：

```
ENABLE=1
NOIRQ=2
NOTIMER=4
```

默认 Mask 可能为 `0x7`。

如果你正在研究异步 Interrupt，希望单步过程中允许 IRQ、但暂时屏蔽 Timer：

```
maintenance packet Qqemu.sstep=0x5
```

研究结束后恢复：

```
maintenance packet Qqemu.sstep=0x7
```

这个设置只改变 GDB/QEMU 的 Single-step 行为，不等于改变 Guest OS 的 Interrupt Enable CSR。

### 技巧五：让 Breakpoint 自动打印上下文并继续执行

调试高频 Domain Switch 时，不必每次手动输入十几个命令。

例如：

```
break sbi_domain_context_exit

commands
    silent

    printf "\n===== DOMAIN EXIT =====\n"
    printf "PC = %p\n", $pc

    info registers a0 a1 a2 a3
    info registers mepc mstatus satp

    bt 4

    continue
end
```

这样每次进入函数时，GDB 都会记录关键上下文并继续运行。

如果要记录 Domain Name，可以在 `switch_to_next_domain_context()` 处使用：

```
break switch_to_next_domain_context

commands
    silent

    printf "\n===== DOMAIN SWITCH =====\n"

    printf "FROM: "
    p ctx->dom->name

    printf "TO: "
    p dom_ctx->dom->name

    printf "CURRENT SATP: "
    p/x $satp

    printf "TARGET SAVED SATP: "
    p/x dom_ctx->satp

    continue
end
```

这要求对应结构体的 DWARF 类型和局部变量信息可用。

这一招很适合构建 Domain Switch Trace，而不会像逐条单步那样严重干扰运行过程。

## 9. 推荐建立自己的 `.gdb` 调试脚本

最后，我建议将最常用的 GDB 配置和断点整理成一个脚本，不需要每次手动输入。

可以在 Buildroot 根目录执行以下命令：

```
cat > /tmp/riscv-tee.gdb <<EOF
set pagination off
set print pretty on
set breakpoint pending off
set architecture riscv:rv64

file $SBI_ELF
add-symbol-file $TEE_ELF
add-symbol-file $LINUX_ELF

target extended-remote 127.0.0.1:1234

set logging file /tmp/riscv-tee-trace.log
set logging enabled on

hbreak sbi_init
hbreak sbi_domain_context_exit
hbreak switch_to_next_domain_context
hbreak sbi_hart_switch_mode

hbreak boot_init_primary_runtime
hbreak boot_init_primary_final
hbreak boot_primary_init_sbi_mpxy

hbreak start_kernel

info breakpoints
info threads
EOF
```

脚本中使用的三个环境变量，是前面第 3 节定位 ELF 时设置的 `SBI_ELF`、`TEE_ELF` 和 `LINUX_ELF`。

启动 QEMU：

```
./output/images/start-qemu.sh -- \
    -S -gdb tcp:127.0.0.1:1234
```

另一个 Terminal：

```
gdb-multiarch -q -x /tmp/riscv-tee.gdb
```

之后：

```
continue
```

就可以依次观察整套启动链。

如果 Linux Debug Symbol 没有被编译进去，或者某个函数被优化掉，脚本会在设置对应断点时报错。建议先确认 `info address` 和 `readelf -S`，不要直接用 `set breakpoint pending on` 掩盖这些问题。

### 另外三个实用的排障命令

如果 GDB 无法正确显示源码：

```
info source
show directories
```

并按实际 DWARF 路径调整：

```
set substitute-path /old/build/path /current/build/path
```

如果怀疑 GDB 使用了错误的 ELF：

```
info files
info symbol $pc
x/12i $pc
```

如果怀疑问题发生在 GDB 断点之前，可以重启 QEMU，额外启用 QEMU 日志：

```
./output/images/start-qemu.sh -- \
    -d guest_errors,unimp \
    -D /tmp/riscv-qemu.log \
    -S \
    -gdb tcp:127.0.0.1:1234
```

`guest_errors` 和 `unimp` 对寻找设备模型错误或未实现行为有帮助，但不是完整的 Trap Trace。需要追踪异常时，可以根据 QEMU 当前支持的 `-d help` 选项选择 `int` 等分类。

## 10. 我建议你先实际完成这条调试链

不要一开始就同时追踪整个 Linux + OP-TEE Runtime。先用现有环境做一次完整 Boot Trace：

| 顺序 | 断点                              | 重点观察                           |
| -- | ------------------------------- | ------------------------------ |
| 1  | `sbi_init`                      | `mscratch`、`mstatus`、Boot Hart |
| 2  | `sbi_domain_context_exit`       | 当前 Domain、目标 Domain            |
| 3  | `switch_to_next_domain_context` | Context、`satp`、PMP             |
| 4  | `sbi_hart_switch_mode`          | Next Address、Next Privilege    |
| 5  | `boot_init_primary_runtime`     | OP-TEE MMU、Stack、`tp`          |
| 6  | `boot_primary_init_sbi_mpxy`    | ReqFwd Channel / Shared Memory |
| 7  | `boot_init_primary_final`       | OP-TEE Runtime 初始化完成           |
| 8  | `start_kernel`                  | Linux 入口、`satp`、Stack          |

其中，第 3 步是我认为最值得深入的节点。

在 RP016 的实现中，`switch_to_next_domain_context()` 同时涉及三个关键动作：

```
1. Domain Ownership / Hart Assignment
                |
                v
2. PMP Physical Memory Isolation
                |
                v
3. CSR + Trap Context Save/Restore
```

建议你在这个函数前后分别记录 `satp`、`stvec`、`sscratch`、`sstatus`、`pmpcfg*` 和 `pmpaddr*`，再结合 `sbi_hart_switch_mode()` 的 `mret` 分析真正的安全域切换。

最后提醒一个很容易导致误判的问题：`rp016_m1` 的 OP-TEE 已配置 Debug 构建，但这不代表 Linux、OpenSBI 和 U-Boot 全部具备同等级别的调试信息。 如果 GDB 能识别函数名，却无法显示参数、局部变量或源码行号，应分别检查各组件的 ELF 和编译选项，而不是先怀疑 GDB Stub。

有了这套调试流程，你后面深入 `sbi_domain_context.c`、`thread_rv.S`、`core_mmu_arch.c` 时，就可以直接从真实执行状态分析，而不需要停留在静态源码推导。
